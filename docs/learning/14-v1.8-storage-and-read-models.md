# 14. v1.8 存储、迁移与读模型

本章承接 [事件管道](13-v1.8-contract-sdk-and-pipeline.md)。学习目标不是背表名，而是能回答：某个数字由什么事实算出、配置版本怎样影响解释、数据不足为什么不是零，以及修改后如何保持历史语义。

## 1. 数据所有权

| 存储       | 当前保存什么                                                                                                  | 维护含义                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| MySQL      | 用户/会话/项目权限，模块/页面/功能/工作流定义，指标与评分版本，目录与可信使用源，设置/导出配置，接收/消费状态 | 管理与治理事实；事务、版本和历史有效区间影响结果   |
| ClickHouse | `raw_events`、短期 `object_operation_refs`、`repeated_operation_proofs`                                       | 分析事实；去重、范围、采集完整性和查询预算影响结果 |
| Kafka      | 普通事件 envelope、短期对象操作消息、DLQ 元数据                                                               | 有保留窗口的消息日志；消费积压不是已经可查询的数据 |
| MongoDB    | 当前应用没有使用                                                                                              | 不存在需要同步维护的第三套应用数据库               |

[CoreService](../../apps/api/src/core.service.ts) 展示 API 实际建立的服务和连接；[生产 Compose](../../infra/compose/production.compose.yml) 展示运行依赖。不要用一份历史架构讨论推断当前数据库拓扑。

ClickHouse `raw_events` 是 `MergeTree`，按 `received_at` 月分区，排序键包含 app、env、接收日期、事件、路由、事件时间和 eventId，TTL 为接收时间后 90 天。排序键不是唯一键，写入不自动去重。项目配置里出现某个保留天数，不意味着已经动态改变这张表的 TTL。

[短期通道迁移](../../infra/clickhouse/migrations/003_r4c_repeated_operations.sql) 中，对象材料为 48 小时 TTL，重复证明为 90 天 TTL。TTL 清理是后台过程，不承诺到了秒点立刻物理删除；投影/查询还必须执行时间限制，不能只依赖后台删除。

MySQL 与 ClickHouse 各自编号，`MySQL 004` 与 `ClickHouse 004` 没有一一对应关系。

| ClickHouse 002 | [r4c_directory](../../infra/clickhouse/migrations/002_r4c_directory.sql)                     | 事件关联目录版本                                     |
| ClickHouse 003 | [r4c_repeated_operations](../../infra/clickhouse/migrations/003_r4c_repeated_operations.sql) | 对象短期材料、重复操作证明、SDK collector 列         |
| ClickHouse 004 | [r4c_usage_source](../../infra/clickhouse/migrations/004_r4c_usage_source.sql)               | SDK 使用覆盖诊断列                                   |

[discoverMigrations](../../packages/database/src/migrations.ts) 按三位编号排序，检查重复编号，并为 SQL 计算 SHA-256。每个数据库都有 `schema_migrations`。执行过的 SQL 校验和变化会报错，因此修复线上结构应新增迁移，不能改旧文件后假定所有环境都会得到相同结果。

MySQL runner 使用迁移锁；ClickHouse runner 按 `-- statement-breakpoint` 分隔执行。它们不是跨数据库原子事务，SQL 执行失败也不等于此前 DDL 自动回滚。迁移事故要先检查已执行语句与 migration 记录，再制定恢复措施，不能反复 reset 生产库。

根命令 `pnpm migrate` 和 `pnpm migrate:verify` 会连接配置中的真实数据库，不适合作为无环境确认的阅读练习。保留数据的本地更新按 [当前验收指南](../guides/v1.8-local-acceptance-macos.md) 使用 `./scripts/dev up-preserve`，不要把历史重建步骤套到已有数据上。

## 3. “读模型”在本项目是什么

这里的读模型不全是预先建好的聚合表。大部分流程是：

1. 从 MySQL 取定义版本、历史归属、启用窗口和权限。
2. 从 ClickHouse 有界读取事实并去重。
3. 用 TypeScript reducer 检查关联、完整性和口径，计算观察值。
4. 绑定指标定义，形成 `value/status/reason/sampleSize` 等输入；符合条件时才交给评分。
5. API 返回解释信息，Vue 负责展示数值、缺失、观察状态与原因。

这层分离很有价值：SQL 负责选择数据，纯函数负责可测试的业务语义，绑定层负责解释“哪个事实对应哪个指标”。但不能假定所有文件完全采用同一模式；定位一个数字必须追它自己的入口。

| 读模型       | 入口                                                                                                                                               | 最重要的不变量                                                   |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 项目概览     | [project-overview](../../packages/server-core/src/project-overview.ts)、[overview-facts](../../packages/server-core/src/overview-facts.ts)         | 同一项目/环境/日历范围下组合事实与分数，不制造统一总分           |
| 功能与业务   | [business-facts](../../packages/server-core/src/business-facts.ts)、[business-analysis](../../packages/server-core/src/business-analysis.ts)       | 功能类型、模块页面归属和历史有效窗口参与计算                     |
| 工作流       | [workflow-reducer](../../packages/server-core/src/workflow-reducer.ts)、[workflow-facts](../../packages/server-core/src/workflow-facts.ts)         | 显式实例关联、定义版本、步骤顺序、终态和超时                     |
| 效率/组织    | [efficiency-facts](../../packages/server-core/src/efficiency-facts.ts)、[organization-facts](../../packages/server-core/src/organization-facts.ts) | 完整采集、可信目录、采样与有效分母，不能由观察人数反推应使用人数 |
| 页面运营     | [page-usage](../../packages/server-core/src/page-usage.ts)、[page-usage-binding](../../packages/server-core/src/page-usage-binding.ts)             | 先选范围再按原 session 归组，页面筛选不能制造跳出                |
| 质量评分事实 | [quality-facts](../../packages/server-core/src/quality-facts.ts)、[quality-binding](../../packages/server-core/src/quality-binding.ts)             | 页面起点 cohort、质量采集能力、完整结算和迟到窗口                |
| 错误明细     | [page-quality](../../packages/server-core/src/page-quality.ts)                                                                                     | 已观察错误的去重、分组和稳定分页；不声称错误覆盖完整             |
| 重复操作率   | [repeated-read-model](../../packages/server-core/src/repeated-read-model.ts)                                                                       | 开始事实、投影证明和快照一致，未闭合窗口不能输出正式值           |

## 4. 时间有四种，必须分开看

| 字段/概念              | 含义                        | 常见误用                           |
| ---------------------- | --------------------------- | ---------------------------------- |
| `timestamp`            | 业务事件发生时刻            | 当成 API 接收到消息的时刻          |
| `received_at`          | API 接收时刻                | 认为晚接收一定不属于较早的业务日期 |
| `asOf`                 | 本次查询可见事实的快照边界  | 以为改变 asOf 就扩大了 `from/to`   |
| 项目时区的自然日/周/月 | 将 UTC 时刻解释为业务日历桶 | 固定减 24 小时替代全部日历运算     |

[resolveProjectCalendar](../../packages/event-contract/src/project-range.ts) 统一项目范围：`[from,to)` 左闭右开，预设范围包含今天，周一作为周开始，按项目时区形成日/周/月桶。范围末尾可能是未完成桶；需要完整自然周期的指标不能把它当已闭合数据。时区转换还考虑夏令时重叠和不存在的本地时间，因此不应在页面另写一份日期算法。

不同 API 有不同事实窗口限制。错误明细支持页面上的 7/30/90/180/365 天与自定义选择，但原始存储只有其保留数据；质量事实 endpoint 本身还限制最多 89 天，并要求不查未来。一个范围能被路由接受，不意味着每个指标都具备完整历史覆盖。

### 错误明细的快照分页

`PageQualityStore.read` 同时限定：项目、env、`timestamp >= from && timestamp < to`、`received_at <= asOf`。SQL 按 eventId 去重；`qualityOccurrencePage` 再做保护、筛选与排序。默认 `latest` 每个错误组展示最新一次；`all` 展示全部去重后的 occurrence。

cursor 包含筛选 scope 摘要、asOf 和上一页末尾位置，并使用 HMAC 签名，一小时过期。切换环境/日期/类别后复用旧 cursor 会失效。查询设有 50,000 条结果预算及执行/扫描限制；超预算时应缩小范围，不要删除 LIMIT 后把管理台变成无限扫描接口。

R8 的显式刷新会推进预设日期范围并清理 cursor；自定义范围保持不变。浏览器后退/重载依然可保留 URL 的固定快照，这与用户主动刷新是不同动作。

## 5. 身份、组织和维度不是可随意补齐的标签

[pageUsageWindow](../../packages/server-core/src/page-usage.ts) 的 UV 身份为登录用户优先（`u:`），否则设备（`d:`）；VV 是原 session 去重。未登录设备不能换算成唯一员工数；中途登录可能使身份口径发生变化，产品应保留其真实含义。

[organization-directory.ts](../../packages/server-core/src/organization-directory.ts) 按环境、发布时间、事件时间和有效期选择目录。后发布版本替代前版本，即使后来版本已过期也不能“复活”更早的目录来凑分母。目录条目中的 `eligible` 决定合格人群；客户端部门声明会被服务端覆盖。

组织渗透计算需要可信目录、完整自然桶、历史目录一致性、可信使用源与采集覆盖等证据。当前 [organization-facts.ts](../../packages/server-core/src/organization-facts.ts) 还有小组规模及有效样本门槛。看到被抑制、观察或缺失状态，不应靠扩大 join、使用当前目录重写历史、把未知成员塞进某部门来修复页面。

`env` 是事实隔离边界；release、页面、模块、组织、浏览器等维度有各自允许的组合和口径。评分查询身份在 [scoreQueryIdentity](../../packages/server-core/src/score-evaluation.ts) 中包含上下文，不是仅按项目缓存一个结果。新增维度需要同步事实读取、分母、历史归属、绑定和缓存/快照身份，不能只给 SQL 加 `GROUP BY`。

## 6. 缺失、观察值和零值

以质量事实为例，[reduceQuality](../../packages/server-core/src/quality-facts.ts) 先选择 `[from,to)` 内开始的 page view，再关联终结与请求事实。未启用对应 collector、未登录、页面未分类、已知传输损失、冲突、终态缺失、迟到窗口未关闭，都可能阻止正式计算。

它不会仅凭错误事件推算“请求失败率”，因为没有可靠的总请求分母。错误明细也不会要求所有错误都有 `qualityVersion`；这解释了“错误列表有内容，但质量分数仍不足”的合理情况。

| 返回信息                         | 应怎样理解                                   | 错误处理                     |
| -------------------------------- | -------------------------------------------- | ---------------------------- |
| `value: 0` 且状态可用            | 定义、覆盖、分母、窗口等条件允许，结果确为零 | 随意改成“无数据”             |
| `value: null` + `reason`         | 当前无法按正式定义计算                       | 前端 `value ?? 0` 后照常评分 |
| `observedValue` 有值、正式值为空 | 存在观察证据，但完整性/成熟度等未满足        | 把观察值作为正式评分输入     |
| 错误明细 `no_data`               | 当前筛选与保留范围内没观察到错误             | 宣称系统零错误、稳定性满分   |
| API 失败                         | 查询没完成                                   | 清空数据并伪装成真实零值     |

[readRepeatedRate](../../packages/server-core/src/repeated-read-model.ts) 是一个易读例子：它返回 numerator、denominator、observedValue、value、reason 与 asOf；投影不完整、实例冲突、保留范围不够、窗口未成熟、少于 5 个相关 session 都阻止正式值。每个指标的 reason 和状态枚举可能不同，不要把此门槛机械套给全部指标。

## 7. 跟读练习与检验

**练习 A：为什么一条已写入错误没有出现在列表？** 手画以下三个条件：事件发生 10:05，接收 10:07；查询 `[09:00,10:00)`，asOf 为 10:10。

预期答案：事件时间不在范围，即使接收时间早于快照也不出现。预设范围显式刷新到 10:10 后可出现；自定义历史范围不应自动扩大。

**练习 B：同一 eventId 两次写入，数字会怎样？** 阅读 `qualityOccurrencePage`、`reduceQuality`、`pageUsageWindow`，比较各自去重位置和冲突检测。

预期答案：都不能把重复当新行为，但处理策略并不完全相同。质量 reducer 还检测同 ID 不同内容冲突；不要推断所有现有查询都有同样的冲突诊断。新指标必须有自己的重复/乱序/冲突测试。

**练习 C：改变部门后，历史数据该自动归到新部门吗？** 追踪 `directoryAt`、consumer `directory_version_id`、`organizationWindowReason`。

预期答案：不能。事件与历史目录版本关联，跨版本窗口还可能不满足正式比较条件。当前组织表不是所有历史事件的解释来源。

**练习 D：不连数据库检验关键算法。** 依赖安装后可运行：

```bash
pnpm exec vitest run packages/event-contract/test/project-range.test.ts packages/server-core/test/page-quality.test.ts packages/server-core/test/page-usage.test.ts packages/server-core/test/quality-facts.test.ts packages/database/test/migrations.test.ts
```

预期：用例覆盖范围、去重/分页、使用与质量事实，以及迁移发现/执行约束。这些单元结果不等于新 SQL 已在你的已有数据上完成升级；真正升级仍要以当前迁移、备份恢复和验收流程验证。

最后尝试用自己的话解释一个完整数字：输入事件 → 定义及时间窗口 → 去重/归约 → 分子分母 → 状态原因 → 指标绑定 → 页面。能说清这条链，才算理解了该功能的维护边界。
