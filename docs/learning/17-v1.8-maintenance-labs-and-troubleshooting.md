# 17. 从会读代码到能维护：实验、排障与变更方法

本文对应 R8 `641e106252e7053ea9a306fddcbc1c80ad66592e`，包含 `4948ece` 质量刷新修复。命令均从仓库根目录执行。学习实验使用独立本地测试栈；生产操作以 [Ubuntu 指南](../guides/production-ubuntu-22.04.md) 和实际维护窗口为准。

## 1. 先分清三种验证

| 验证层               | 运行入口                              | 能证明什么                                                   | 不能证明什么                   |
| -------------------- | ------------------------------------- | ------------------------------------------------------------ | ------------------------------ |
| 静态检查、单元与构建 | `pnpm check`                          | 格式、工作区边界、生成物、规范名、lint、类型、单元逻辑、构建 | Kafka/数据库/浏览器真实协作    |
| 真实服务集成         | `./scripts/dev smoke`、各 `verify-r*` | 实际管理元数据、事件写入与读取、迁移、权限                   | 所有用户点击与浏览器生命周期   |
| 浏览器产品链路       | `pnpm test:r8:e2e` 及对应阶段 E2E     | Chromium/WebKit 下 UI、SDK 和服务链路                        | 真实部署机器容量、最终业务批准 |

不是所有 Playwright 用例都使用真实后端。R8 的 `quality-refresh.spec.ts` 拦截 API，专门验证时间与 URL；`demo-quality.spec.ts` 才从真实 demo 经 ingestion 和存储验证 occurrence。阅读测试开头、fixture 和配置后，再解释它的证明范围。

当前 [R8 完整工作流](../../.github/workflows/v1-8-r8.yml) 是完整回归顺序的权威入口；[生产工作流](../../.github/workflows/production-deployment.yml) 使用独立生产 Compose；[文档工作流](../../.github/workflows/v1-8-r8-docs.yml) 只运行格式及规范名检查。绿色文档 CI 不能当作应用回归成功。

## 2. 建立可复现的学习环境

先记录 `git status --short` 与 `git rev-parse HEAD`，不要把已有工作覆盖。源码检查使用 Node ≥24、仓库锁定的 pnpm 11.15.1，版本来自根 [package.json](../../package.json)，依赖来自 lockfile：

```bash
node --version
pnpm --version
pnpm install --frozen-lockfile
pnpm check
```

依赖安装完成不等于服务已启动。目标本地环境是 Apple Silicon + Docker Desktop/Compose v2；首次创建独立学习栈：

```bash
./scripts/dev doctor
./scripts/dev bootstrap
./scripts/dev up
./scripts/dev smoke
./scripts/dev status
pnpm exec playwright install chromium webkit
```

管理端默认 4173，demo 默认 4174。账号与完整步骤见 [本地验收指南](../guides/v1.8-local-acceptance-macos.md)。`up` 会运行本地 seed；已有配置和数据需要保留时使用 `./scripts/dev up-preserve`，不要为排障重复初始化。`down` 保留卷；`reset --confirm-local-data-loss` 删除该本地栈数据，不是普通重启。

[scripts/dev](../../scripts/dev) 的 `doctor` 包含 arm64、Docker、内存和磁盘检查。CI 的 `M5_ALLOW_NON_ARM64=1` 是隔离 runner 的显式配置，不代表任意机器都满足正式环境要求。生产无需在宿主安装 Node/pnpm，使用镜像内工具链和 `scripts/production`，不要用学习栈替代生产入口。

## 3. 第一组实验：解释这次质量刷新故障

**目标：** 学会区分“事件没产生”“事件没入库”“查询范围没包含事件”。

先跟读以下三个文件：

- [PageQualityView.vue](../../apps/web/src/views/PageQualityView.vue)：`signature`、`load`、`filterNavigation`、`refresh`；
- [quality-refresh.spec.ts](../../tests/v1.8/r8/quality-refresh.spec.ts)：固定时钟、模拟传输与查询参数断言；
- [demo-quality.spec.ts](../../tests/v1.8/r8/demo-quality.spec.ts)：HTTP 202、特定 occurrence 的轮询、环境隔离与 UI 断言。

在独立栈启动后运行：

```bash
pnpm exec playwright test --config playwright.r8.config.ts quality-refresh.spec.ts
pnpm exec playwright test --config playwright.r8.config.ts demo-quality.spec.ts
```

两个命令默认各跑 Chromium/WebKit。第一项只需可访问的管理端静态页面，API 被模拟；第二项需要 seed 项目、demo、API、Kafka、consumer 与 ClickHouse 全部运行。不要只运行第一项便声称链路已通过。

手工跟读实验：

1. 打开 demo 项目的页面分析质量页，选择 `dev` 和最近 7 天，记下 URL 的 `from/to`。
2. 在实验室触发“模拟 JS 异常”。只在本地查看事件的 `appId/env/timestamp/eventId`，不要收集登录凭证。
3. 观察 HTTP 202。再等待匹配的 occurrence 出现在查询结果中，避免把别的历史错误误当本次结果。
4. 点击质量页的“刷新”，比较新的 URL `to`；然后切换 `staging/prod`。
5. 换成截止于触发错误之前的自定义时间，再次刷新。

**预期与解释：** 预设范围刷新按项目时区推进到当前时间，清理旧 cursor 和派生评分边界；自定义时间保持不变。demo 实际上报 `dev`，所以这条错误不应出现在其他环境。F5 或分享链接保留 URL 时间快照，与页面按钮不是同一个语义。`asOf` 是查询快照时间，不能替代事件时间的 `to`。范围通常按 `from ≤ timestamp < to` 过滤，因此新快照仍可能查不到范围外的新事件。

**自测问题：** 为什么不能用“所有刷新都把 to 改成现在”修复？答案是会破坏历史自定义范围、分页/链接的可复现性。为什么切环境没解决旧缺陷？它没有改变旧的时间边界。完整原因见 [修复记录](../progress/v1.8-r8-quality-refresh-fix.md)。

## 4. 第二组实验：从分数追到事实

从一个项目的指标管理打开运营或质量分数，记录版本、绑定范围、事实状态与贡献。按 [领域与评分章节](15-v1.8-domain-analysis-and-scoring.md) 跟到服务，然后读取以下测试：

- [score-evaluation.test.ts](../../packages/server-core/test/score-evaluation.test.ts) 与 [quality-score-evaluation.test.ts](../../packages/server-core/test/quality-score-evaluation.test.ts)：独立评分与边界；
- [score-management.test.ts](../../packages/server-core/test/score-management.test.ts)：版本和管理语义；
- [page-usage-binding.test.ts](../../packages/server-core/test/page-usage-binding.test.ts)：页面事实和绑定。

```bash
pnpm test:r1c
pnpm test:r6
```

在测试用例中选一个有手算输入的 fixture，自己写出“分子、分母、门槛、方向、目标、权重、结果”，再对照断言。接着找一个缺目标或缺事实的用例，解释为什么不能写成 0。不要为得到绿色结果修改 golden/snapshot 的业务期望。

**交付标准：** 能解释页面某个分数为何可计算或不可计算，指出事实来源、版本、时间范围，以及哪个测试保护这条规则。仅知道函数名不算完成。实验如需编辑 fixture，在自己的练习分支操作，不发布指标或改变正式项目配置。

## 5. 第三组实验：事件重复和工作流乱序

先阅读 [workflow-reducer.test.ts](../../packages/server-core/test/workflow-reducer.test.ts)、[workflow.test.ts](../../packages/web-tracker/test/workflow.test.ts)、[durable-offsets.test.ts](../../apps/consumer/test/durable-offsets.test.ts)。然后执行：

```bash
pnpm test:r4b
pnpm exec vitest run apps/consumer/test/durable-offsets.test.ts
```

画出一个实例的开始、步骤、终态时间线，再选测试里的乱序、并发实例或重复事件路径解释结果。分别回答：`eventId` 去重解决什么？`workflowInstanceId` 关联解决什么？消费者 offset 何时可以提交？为什么最终查询正确不代表原始表没有重复行？

**预期：** 两种 ID 不是同义词；一个用于同一事件的身份，一个用于一项业务执行实例的关联。Kafka 重放与查询去重共同决定结果，不能假设 exactly-once。首个终态、超时、缺步骤等处理按 reducer 的明确规则，不用“最后到达覆盖一切”推测。更完整链路见 [契约与消费章节](13-v1.8-contract-sdk-and-pipeline.md)。

## 6. 面对故障，沿最短证据链定位

| 现象                    | 优先检查                                                   | 分层判断及下一步                                    |
| ----------------------- | ---------------------------------------------------------- | --------------------------------------------------- |
| 点击操作后没有事件      | SDK 是否初始化、功能是否启用、是否显式报告终态、是否 flush | 查 SDK/业务调用；按钮点击不等于业务完成             |
| `/v1/events` 被拒绝     | 响应拒绝码、精确 Origin、项目、v3 契约                     | 查 ingestion；不要先重建数据库                      |
| 202 但查不到            | 项目/env/时间、consumer 状态、offset/写入失败、链路延迟    | 202 是接收阶段证据；查实际写入和读模型              |
| 质量页仍是旧错误        | 显式刷新、URL `to`、类别/页面/组/cursor                    | 区分历史窗口与新快照；不要关闭环境过滤              |
| 工作流数量异常          | 实例 ID、首个终态、超时、重复及缺步骤                      | 查 reducer fixture，再查原始受控事实                |
| 指标空白但存在访问      | 分母、目标、样本、版本绑定、事实采集状态                   | “有 PV”不代表所有指标可计算                         |
| 403 或找不到项目        | 登录状态、全局角色、项目成员角色                           | 查 API 授权；UI 隐藏不是安全边界                    |
| 快速切项目后显示旧结果  | 请求 scope、AbortController、generation 和卸载             | 查对应 view；不要假设所有 view 都通过同一 hook 实现 |
| 新版本部署无法读 secret | 文件权限、实际容器 UID/GID、挂载                           | 用生产 doctor/指南排查，不重新生成旧数据库密码      |
| CI 浏览器依赖失败       | 失败步骤是否安装浏览器/系统包而非断言                      | 区分 runner 网络故障与代码缺陷，保留同 SHA 重跑证据 |

先使用 `./scripts/dev status`、`./scripts/dev logs consumer` 等有限日志入口。分享问题时只提供脱敏的错误码、请求 ID、时间、env、项目和提交，不复制整份 Authorization、Cookie、secret 或完整用户内容。项目已有受控采集和日志策略，维护时不要为方便调试直接打印完整 payload。

## 7. 常见修改落点与最小回归

| 修改                   | 源码与契约起点                                                                           | 优先回归                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 新增/调整事件字段      | event-contract 的规范字典/生成脚本 → Schema 和类型 → SDK → ingestion/consumer → 存储迁移 | `contract:check`、`canonical:check`、契约 fixture、SDK、真实链路 |
| 改分析对象或工作流配置 | server-core 分析对象服务 → API controller → 管理端                                       | R1-A、R4-B；已有实例和版本语义                                   |
| 改公式或分数           | 公式 AST/DAG、评分 evaluator、metric/score 管理与绑定                                    | R1-B/C golden、真实数据库与页面                                  |
| 改页面质量/运营        | 对应 facts/read model → controller → view                                                | R5-A/B 或 R6；分母、匿名、env、时区、缺失状态                    |
| 改设置/权限/外部接口   | settings/auth/store → controller → view                                                  | R7、admin/viewer、项目隔离、撤销与审计                           |
| 改导航/刷新/URL        | router/project context/view 请求状态                                                     | R8；深链接、返回、并发旧响应、刷新范围                           |
| 改数据库结构           | 新增 migration，保留已应用文件                                                           | 空库 + 保留数据升级；相关查询与备份恢复                          |

命令是否存在以 [根 scripts](../../package.json) 为准；集成入口看 [scripts/dev](../../scripts/dev)。不要从旧 M0–M5 文档复制已删除的路由或 `seed:r0` 命令。局部修改先跑能暴露该风险的测试，再按仓库发布门进行完整回归；纯文档改动不需要重跑故障注入和生产部署。

## 8. 把学习变成可评审的维护交付

每次练习或修复写一小段记录：

- **问题和范围：** 谁看到什么，期望什么，使用哪个提交/环境/时间窗口；
- **原因：** 哪个输入或状态违反了哪个不变量；给到源文件和具体函数；
- **修改：** 改哪些层，旧行为如何兼容，历史数据是否受影响；
- **证据：** 原用例如何失败，新用例如何通过，mock 与真实链路分别证明什么；
- **边界：** 实际执行命令和 SHA，未验证环境、业务批准或手工复验。

接手维护前应独立完成：解释一条事件全链路、手算一个指标、解释一个不可计算状态、定位一次 403、复现质量刷新差异、在练习分支完成一项小修改及回归。第一次正式维护建议选择一个已有明确失败用例的小缺陷，完成评审后再进入跨契约/迁移的修改。

当前项目的 CI、手工验收、R7 真实异常规则批准和目标服务器验证是不同的门。最新状态始终查 [R8 results](../progress/v1.8-r8-results.md)，不要把学习练习完成写成最终发布通过。
