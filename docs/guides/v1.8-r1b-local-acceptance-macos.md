## 4. 系统默认指标目录

1. 使用管理员进入“指标管理 → 运营指标”；
2. 检查“系统默认指标”和“用户业务指标”明确分区；
3. 运营目录应有 19 个 key，切换质量指标应有 16 个 key，合计 35 个 §2.6 保留 key；
4. 分类只能是 `usage/operation/performance/stability/organization`；
5. 每行显示规范 key、中文名、implementation status、`availableFrom` 或不可用原因；
6. 打开定义抽屉，逐项检查业务说明、公式、分子、分母、去重键、单位、分位数、上报时机、scope、时间粒度、minimum sample、missing policy、owner、版本和 milestone；
7. `partial/not_collected` 的定义可查看，但 UI 不显示 0、0%、空趋势或近似值；
8. 页面没有编辑或删除系统指标的入口。

API 抽查：

```bash
curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/projects/11111111-1111-4111-8111-111111111111/metrics/catalog?type=operational"
```

不得在日志、截图或共享文档中保存真实 token。

## 5. 保留 key 与旧 key 负向验收

1. 从 catalog 响应取任一系统 key，对草稿的 definition PUT；预期 409 `SYSTEM_METRIC_KEY_RESERVED`；
2. 尝试删除系统 key；产品 UI 不提供入口，服务端不得删除 system origin 行；
3. 从生成的 `FORBIDDEN_ALIASES.metricKeys` 测试任一已删除旧 key；预期 410 `METRIC_KEY_REMOVED`；
4. 响应不得返回 canonical key，不得创建 alias，不得自动重写请求；
5. R1-C 保留的 score key 同样不能被用户业务指标占用。

不要在新业务代码里重新硬编码旧 key；负向测试从生成契约读取，以继续接受 canonical scanner 约束。

## 6. 语义化公式编辑器

在运营指标中点击“新建业务指标”：

1. 确认没有 SQL、代码、字段名或任意函数文本框；
2. 输入指标只能从已注册指标中搜索；
3. 运算符列表只能出现 `+ - * / min max clamp weighted_mean normalize`；
4. 可配置目标/方向、输出单位、entity scope、时间粒度、minimum sample、分子/分母、去重键和 missing rule；
5. 前端对 key 冲突、缺少输入和明显单位冲突给出即时提示；
6. 保存后必须显示“服务端权威校验”结果；前端不计算业务结果，也不维护第二套 evaluator；
7. 选择 `pv / vv` 时输出单位填写 `views_per_session`，保存成功；
8. 输入不兼容单位做加法，服务端返回 `FORMULA_UNIT_INCOMPATIBLE`；
9. 分母为 0 的 evaluator fixture 返回 `metric_not_available`，不是 0；
10. null、样本不足、数据延迟按原状态传播，不允许 `coalesce(..., 0)`。

## 7. 公式安全负向验收

专项测试必须证明：

- 字符串或 SQL-shaped AST 被拒绝；
- AST 出现 `sql`、`field`、`projectId` 等任意字段被拒绝；
- `eval`、`coalesce` 或其他未批准函数被拒绝；
- 20 个输入通过，第 21 个失败；
- 8 层通过，第 9 层失败；
- 100 节点通过，第 101 节点失败；
- 同单位加减和 scalar 乘除通过，非法单位组合失败；
- 缺失依赖、跨项目引用和 DAG 循环 fail fast；
- `clamp` 边界必须是受控 literal；normalize 目标顺序必须合法。

运行：

```bash
pnpm vitest run packages/server-core/test/formula.test.ts
```

## 8. 三个固定手算 fixture

| 业务指标               | 输入                               | 手算                      | 预期 |
| ---------------------- | ---------------------------------- | ------------------------- | ---: |
| `pages_per_visit`      | views=120、session count=40        | `120 / 40`                |  `3` |
| `weighted_activity`    | A=80、B=60、权重 3/2               | `(80×3 + 60×2) / 5`       | `72` |
| `latency_target_score` | value=300、target=100、ceiling=500 | `100×(500-300)/(500-100)` | `50` |

总值和两个趋势桶必须调用同一 evaluator，并分别得到完全相同的结果。证据在 `packages/server-core/test/formula.test.ts`，完成报告不复制第二套实现。

## 9. 版本生命周期

1. 在 active v1 点击“复制为草稿”，得到 v2 draft，且 `sourceVersionId` 指向 v1；
2. 在 v2 新建/编辑指标并运行服务端校验；
3. 查看 diff，应列出新增、删除或变更字段；
4. 查看影响范围，应列出 downstream metric、display binding 和 score reference；
5. 点击激活，确认框必须同时说明 diff、影响和 active 快照不可变；
6. 激活 v2 后 v1 为 superseded，数据库只能有一个 active；
7. 选择 v1 点击“重新激活旧快照”，v1 恢复 active、v2 变 superseded；该动作不修改 v1 内容；
8. 复制一个新草稿并“废弃草稿”，状态应为 abandoned，不能激活；
9. 在 active 或 superseded 快照点击编辑/删除业务指标，系统必须先复制新草稿，原快照保持不变；
10. `not_collected` 指标若存在 display binding 或 active score reference，激活必须失败并返回 `NOT_COLLECTED_METRIC_BINDING_FORBIDDEN`。

## 10. 血缘与 definition read model

1. 对 `pages_per_visit` 打开血缘抽屉；
2. 检查当前公式和 version id；
3. 直接上游包含 `pv`、`vv`，edges 方向为上游到业务指标；
4. node 展示单位、minimum sample、missing policy、origin 和 implementation status；
5. downstream、display binding、score reference 从服务端 read model 读取；
6. 失效依赖或循环显示服务端 validation error，不渲染为可用结果。

## 11. 权限、隔离、审计和隐私

1. viewer 可查看系统/业务定义、版本、diff、impact 和血缘；
2. viewer 看不到复制草稿、新建、编辑、删除、校验、激活、废弃按钮；
3. viewer 直接调用所有写 API 返回 403；
4. 非成员访问另一项目先返回 403，不泄露版本或 key 是否存在；
5. source version 必须属于同项目、同 library type；
6. AST 不接受 `projectId` 字段，不能引用另一项目指标；
7. `audit_logs` 包含 draft created、definition saved/deleted、activated、abandoned；
8. 审计 metadata 只记录 key/version/type，不保存 AST、SQL、token、header、query、业务对象或用户输入 payload。
