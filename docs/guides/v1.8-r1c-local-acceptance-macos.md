## 3. 管理员：运营完整流程

1. 进入运营分数。现有基线没有完整配置时显示尚未保存，不显示假分数。
2. 点击“复制为工作草稿”或“创建工作草稿”，进入“编辑工作草稿”。重复进入同一来源会复用工作草稿；若另一来源已有草稿，先在版本列表选择它，完成或废弃后再复制。
3. 第一步显式采用系统默认模板，核对 key `operational_score`、中文名、owner、分/%。展示单位不会把底层 0–100 再乘 100。
4. 第二步确认项目/模块范围、项目时区、目标人数、预期星期（1–7，星期日为 7）、核心页面及关键度、页面模板、正式工作流类型权重、时长最低有效样本。缺目标/预期星期时通过“修改目标用户和预期星期”进入既有配置；分析对象仍在指标管理原入口维护。回到分数草稿重新核对并勾选确认。
5. 第三步复核默认四维权重 30/25/30/15。高级配置可设置 3–6 维、指标、方向、目标、最低样本、权重、gate、85/60 色带和雷达。维度权重及每维叶子权重分别合计 1；服务端拒绝非法单位、跨类型依赖及超出受控公式限制。
6. 第四步“校验配置并预览”。正常固定示例为 76.15；部分缺失仍通过 gate 为 82.5294117647（显示按小数位舍入）；不通过 gate 总分为 `—`。检查维度分、实际贡献之和及雷达等价表。合成示例有醒目标记，不是实际项目分数。
7. 故意填非法 key 或权重，保存应显示错误并保留已填中文名/目标；修正后保存草稿。刷新页面，URL 与当前类型、版本一致，保存数据仍在。
8. 在对应指标版本的目录中核对规范 UV 不使用未登录设备兜底；当前目录身份定义版本为 `system-identity-2026-09-09.1`，旧快照仍保留旧定义标记。点击“激活前检查”，查看配置完整性、diff/impact、固定手算、选定范围的独立历史试算。实际事实缺失时历史结果不可用是正确行为；不会把 fixture 写入历史。
9. “确认激活快照”后，该类型只有一个 active。配置状态 active 与事实状态 unavailable 可以同时出现。
10. 复制工作草稿，修改中文名或展示单位，保存并检查 diff；激活新版本，原版本变为 superseded。选择旧版本，执行“重新激活前检查 → 确认激活快照”；旧配置内容不变，增加新的生效区间和审计。
11. 再复制并“废弃工作草稿”。废弃版本仍可查看，不能激活；active 保持原版本。

## 4. 管理员：质量完整流程

对质量类型重复第三节全部生命周期；运营版本不随质量操作改变。

模板 owner 为 Jesse，批准日期/来源/参数版本可查看。默认参数：JS 35%（0.001/0.01、1000 PV）、资源 15%（0.001/0.02、1000 资源请求）、API 30%（0.005/0.05、1000 API 请求）、页面性能 20%（LCP/INP/CLS 权重 50/30/20，最低各 100 有效样本），均 lower_better。性能目标/ceiling 分别 2500/4000 ms、200/500 ms、0.1/0.25。

正常固定示例 72.9532163743；健康零错误示例中三个稳定性维度为 100，性能仍按其实际示例输入计算，不能仅因为零错误宣称总分 100。无数据示例总分不可用。默认 gate 为 healthy、至少 3 维、至少 70% 叶子权重覆盖、来源曝光完整、同项目/env/版本/范围。freshness 只作为 gate。

系统模板升级需显式采用；保存项目快照不自动跟随模板变化。JS/Web Vitals 仍 partial，API/resource rate 仍 not_collected，不能改标签或用 PV 替代其他请求分母。

## 5. 解释、真实不可用与历史

- 已保存版本可看完整配置、真实指标定义版本/依赖、分析对象 revision、模板、范围、样本策略和生效区间。
- 原始值、单位、目标、最低/有效样本、得分、配置权重、实际权重、贡献、状态和原因逐项可见。实际样本未知显示 `—`，不写成 0；显示有效、排除、未识别样本的未知原因。
- 雷达只画 0–100 维度分，与表格一致；不可计算的点不画成 0，不使用不同单位原始值。
- 选择 prod/staging/dev 及 UTC 起止范围，刷新查询；结果同时说明项目时区，URL、范围、类型及版本一致。快速切换类型/页面后旧响应不得覆盖新选择。
- Q04 单个项目本地日期无法观察跨日持续；Q05 保留既有会话边界，窗口 P50 不平均每日桶。跨午夜和部分日期解释见 ADR-019。
- “保存历史试算”生成独立记录，可由 viewer 查看；旧试算保留当时定义版本、参数和范围。改草稿不会给旧结果换版本标签。跨版本范围无混算总分，无事实不伪造趋势。
- 当前真实工作流/质量真分母/规范使用事实及 env 完整性尚未齐：R4-B/R5-A/R6 分别验收实际数值和事实血缘。这里应看到具体不可用原因和真实定义依赖，不期待当前项目被 fixture 填出分数。

## 7. 自动化与真实集成

在专用本地测试栈运行以下命令。verifier/browser 会创建和废弃验收草稿、激活验收版本并写入审计，不用于生产；R1-A/B 先运行，再运行 R1-C，避免不同阶段的 active/draft fixture 互相影响。

```bash
pnpm check

pnpm test:r1b

./scripts/dev verify-r1b
./scripts/dev verify-r1a
pnpm test:r1b:e2e
pnpm test:r1a:e2e
./scripts/dev verify-r1c
pnpm test:r1c:e2e
```

`verify-r1c` 同时保留无副作用 preflight 回归和完整真实 MySQL/API 生命周期、权限、审计、历史及不可用行为验证，输出持久证据 `artifacts/r1c-integration.json`。R1-C 浏览器矩阵当前为每个浏览器两类 admin 全流程、两类 viewer 读取流程及旧响应隔离，共 10 条；R1-B 的 4 条和 R1-A 的 6 条单独保留，不能替代它们。

## 9. 排错与验收记录

| 现象                                      | 处理                                                                          |
| ----------------------------------------- | ----------------------------------------------------------------------------- |
| Docker 缺失、engine 未运行或架构错误      | 启动原生 arm64 Docker Desktop，执行 `./scripts/dev doctor`；检查 Compose v2   |
| 登录失败                                  | 确认 up/seed 成功、ASCII 密码；查看 `./scripts/dev logs api`                  |
| 新接口 404 或缺数据库列                   | 核对 HEAD，重新 up 构建与迁移；不要只启动旧 API 镜像                          |
| `SCORE_BUSINESS_REVISION_CHANGED`         | 分析对象/目标已变化；刷新业务配置后重新确认，未保存输入先复制留存             |
| `SCORE_BUSINESS_CONFIGURATION_INCOMPLETE` | 确认目标、预期星期、范围内核心页面和已激活正式工作流；不以独立 operation 代替 |
| `SCORE_ACTIVATION_REVIEW_REQUIRED`        | 草稿或依赖在上次预检后变化；重新执行激活前检查                                |
| `METRIC_LIBRARY_DRAFT_EXISTS`             | 选择现有工作草稿继续，或明确废弃后再从另一版本复制                            |
| active 但 unavailable                     | 区分配置与事实状态；查看具体来源、样本或版本边界原因，不补 0 或假血缘         |
| 本地 pnpm 启动器异常                      | 使用仓库锁定 pnpm 11.15.1；不能把未完成的 check 记为通过                      |

验收反馈请记录 HEAD、浏览器、角色、类型、版本、操作步骤、期望/实际结果及 requestId。最后 `./scripts/dev down` 保留数据。验收通过后由 Jesse 决定合并与下一阶段，代理不自动操作。
