## 用项目概览做每日检查

**前提：** 当前项目和环境已选对；正式分数还需要已激活配置和足够事实。入口是左侧“项目概览”。

1. 先读“链路与数据状态”：最近数据更新时间、可用起点、状态作用范围及“环境健康已验证／未验证”。项目级健康提示不能代替当前环境的接入证明。
2. 展开“范围、来源与版本身份”，核对查询窗口、粒度和数据身份。记录运营、质量各自的版本，二者独立。
3. 阅读“运营分数”“质量分数”的原因、维度和贡献。缺少一项时先看缺失原因；不要把观察值或空白分数手工补为 0。
4. 浏览“运营指标”，打开指标解释；再选指标看“指标变化趋势”。需要新增卡片时，管理员使用“配置概览展示指标”，只读用户使用“查看指标定义”。
5. 查看“固定告警摘要”，点击“查看告警证据”，判断是链路、样本、分数还是业务变化需要跟进。

**预期：** 获得一条带依据的结论，例如“dev 项目本周已有页面访问，但任务事实不足，运营总分不可用”；不要简化为“项目没用起来”。

“刷新数据”失败时页面可能保留上次数据并显示 `stale`。等待恢复或点击“重试”，记录旧数据身份；这里不要套用质量分析“刷新会推进预设范围”的专门规则，需核对顶部窗口是否覆盖你关注的时刻。

## 用业务分析定位模块问题

入口：“业务分析” → “功能模块”。建议每次先分析一个模块，避免混合不同业务任务。

| 步骤 | 看哪里                               | 可以回答的问题                             |
| ---- | ------------------------------------ | ------------------------------------------ |
| 1    | 项目、环境、范围、运营版本和数据状态 | 当前结果是不是我要比较的同一口径？         |
| 2    | “模块指标”及“解释 …”                 | 数值来自什么、样本够不够、为何只有观察值？ |
| 3    | 卡片“显示趋势”和“指标变化趋势”       | 变化发生在哪段时间，是否跨版本或缺数据？   |
| 4    | “页面构成与观察证据”                 | 访问集中在哪些页面，是否有未归类事实？     |
| 5    | “模块渗透率的来源”                   | 分子和分母的来源是否足以支持正式比率？     |
| 6    | “操作效率”“工作流追踪”               | 用户是否完成任务，在哪里等待、失败或重复？ |
| 7    | “组织维度”                           | 已闭合周期里，哪些受控群组有使用观察？     |

卡片的“正式值”“观察值”“样本”“原因”一起读。例如观察到 30 次操作不意味着采集覆盖了全部操作；正式值可能仍不可用。若没有卡片，点击“查看指标配置与版本”，核对运营版本里的“业务分析展示指标（版本化）”绑定，不要仅检查 SDK。

若提示 `BUSINESS_ACTIVE_VERSION_CHANGED`，使用“读取当前激活版本”；如果目的是回看旧版本，保留旧链接和版本身份，避免混成一次同比比较。

## 工作流：从结果进入阶段和实例

**前提：** 管理员配置并激活了工作流；业务应用按定义产生关联事件。只创建工作流名称不会自动获取任务过程。

1. 在“工作流追踪”找到任务和定义版本，分别阅读开始数、进行中、成功、失败、取消与近似超时。
2. 点击“查看 [工作流名] v[版本]”，打开“工作流详情”。
3. 看“阶段漏斗与相邻阶段耗时”，判断损失发生在哪个阶段；看“开始 cohort 趋势”判断不同启动批次的变化。
4. 在“安全实例证据”核对个例，必要时分页；点击“查看工作流定义与版本”追溯当时的步骤条件，而不是拿现在的草稿解释旧事实。

口径要点：

- 实例按**开始时间**归入窗口，终态观察截至页面显示的 `asOf`。今天开始、之后结束的任务，其结果可能随迟到事实更新。
- `approximate_abandoned` 是超时近似放弃，不能当作确定业务失败；“进行中”也不是失败。
- 不同定义版本单列。改了步骤、顺序或终态策略后，不应直接合并漏斗。
- 总耗时 P50/P90 基于有效成功耗时样本；显示不足 5 个样本时，不应据少数个例给出稳定性结论。
- “已观察到兼容 SDK”证明看到了相关来源，不证明所有客户端、流程和终态都完整覆盖。
- 请求技术成功不等于业务成功，页面离开也不能证明任务完成。应与接入开发者确认所采用的步骤触发方式。

**示例：** “下载模型”成功率下降时，先看是否新增了未完成实例，再查看“发起下载 → 请求完成 → 业务完成”的步骤定义。若请求返回成功但业务拒绝，必须依赖业务操作结果或显式完成事实；不能因 HTTP 200 把它改判成功。

## 操作效率：一起看结果、样本和生命周期

“操作效率”包含表单效率、业务操作结果、重复操作等观察。使用时先核对范围和覆盖说明，再比较趋势。

| 指标方向     | 正确理解                                                 | 常见误读                       |
| ------------ | -------------------------------------------------------- | ------------------------------ |
| 表单效率     | 以已结算的表单生命周期为依据，未提交会话不硬塞进提交比率 | 把未提交都算提交失败           |
| 业务操作结果 | 技术失败、业务拒绝、成功、未知有区别                     | 把接口 200 都算业务成功        |
| 重复操作     | 按系统配置的相关窗口和事实判断，不代表用户能力           | 将重复点击直接解释为员工低效   |
| 耗时         | 看有效样本、单位、P50/P90及缺失原因                      | 混用秒和毫秒，平均不同组的 P50 |

需要细化业务成功、对象关联或表单结算时，由接入开发者按 [R4-C 接入与验收说明](../v1.8-r4c-local-acceptance-macos.md) 和 [领域分析学习文档](../../learning/15-v1.8-domain-analysis-and-scoring.md)核对，运营用户不应通过修改分数掩盖事实缺口。

## 组织维度：什么情况下有正式使用率

组织聚合依赖管理员发布的组织目录、正确身份关联、可验证的使用来源以及已闭合并结束迟到期的项目日历桶。平台登录成员列表不能充当业务员工编制。

1. 看“组织维度”的状态和原因，再看每桶的目录版本与接入声明。
2. 对比活跃人数、编制人数、正式／观察使用率；无完整使用来源时按观察解释。
3. 看“角色 × 模块 PV Top 20”和有效可见时长，提出功能采用或页面目标问题。
4. 若缺目录，点击“查看组织目录配置与版本”，由管理员确认并发布；新版本向后生效，不补造历史。

当前实现中，任一部门、角色或模块分组不足 5 人时，同一结果族整体隐藏；没有人员明细。缺少有效 `page_leave` 时，有效时长排名也可能不可用。组织目录不完整、使用事件不完整、小组隐藏是不同原因，应按页面提示分别处理。

## 每周复盘建议

交付一份短记录即可：项目／环境／窗口与时区、运营和质量版本、三个主要变化、相应样本与限制、证据链接、待管理员或开发者跟进的动作。不要将页面停留长直接视为好事：驾驶舱、信息分析、任务操作的合理目标不同。
