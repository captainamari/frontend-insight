# 01 · 快速上手与角色

[返回目录](README.md) · 下一篇：[项目概览与业务分析](02-overview-and-business.md)

## 登录前准备

向平台维护者取得平台地址、已有账号及项目访问权限；再向接入同事确认业务应用对应的项目、`appId`、实际环境和数据开始采集时间。不能仅凭业务网址猜测数据上报到哪个环境。

打开平台并登录，进入“全部项目”。当前登录界面用于现有账号认证，不提供完整的自助注册、找回密码或账号审批工作台；相关需求联系维护者。生产账号不要使用开发验收文档里的测试账户。

## 账号角色与业务职责

| 条件／职责                             | 能做什么                                                                                 | 不能据此推断什么                                        |
| -------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 全局 `viewer`，且可访问项目            | 查看项目数据、定义、版本和解释；受控证据按授权显示                                       | 项目内标为 owner 不会自动突破全局只读限制               |
| 全局 `admin`                           | 对存在的项目，系统赋予有效项目角色 `admin`，可配置项目、分析对象、指标、成员、探针及接口 | 不需要额外添加 admin 成员，但不能跳过校验或异常规则审批 |
| 全局 `admin` 且为实际项目 `owner` 成员 | 除管理功能外，可登记异常规则的真实审批证明                                               | 全局 admin 身份本身不能替代该 owner 成员条件            |
| 无项目权限                             | 无法读取该项目，出现访问错误                                                             | 分享链接不会授予项目权限                                |
| 业务负责人、运营、测试、开发者         | 按自己的工作任务选择阅读路线                                                             | 这些职责不是额外的系统权限角色                          |

日常文档说“管理员”时，指满足服务端写权限的人。当前实现中，全局 admin 对存在项目由 `getProjectRole` 统一返回 admin，且可新建项目，无需逐个加入项目。全局 viewer 即便被登记为项目 owner/admin，仍不能执行这些管理写操作；异常规则的审批登记还额外核对真实 owner 成员关系。分数里的“业务 owner”是责任信息，不会自动创建账户或赋权。项目的登录成员与组织使用率所需的“组织目录”也是两件事。

## 十分钟完成第一次查看

**前提：** 已登录且至少能访问一个项目。没有事件也可以完成导航，结论应记录为待接入／无数据。

1. 在“全部项目”输入项目名称；确认环境选择为业务 SDK 实际发送的 `dev`、`staging` 或 `prod`。
2. 选择“最近 7 天”，阅读卡片状态、运营分数、质量分数和更新时间。`—` 表示不可用，应看原因，不是 0 分。
3. 点击“进入项目”，在顶部核对项目时区、环境、开始和结束时间。
4. 打开“项目概览”，先读“链路与数据状态”，再看分数和指标；点击卡片的解释入口查看依据。
5. 打开“业务分析”，选择一个“功能模块”；看是否有页面事实、工作流事实以及不足原因。
6. 打开“页面分析”：“质量分析”查错误；“运营分析”查页面访问、趋势和目标。
7. 复制当前地址作为自己复查的链接；向别人分享时，同时说明项目、环境和时间范围，接收者仍需有权限。

**预期：** 你能指出当前看的是什么范围、哪些数据可用、下一步应找谁。若项目列表为空，先清空搜索；仍为空时联系管理员核查授权。不要通过新建同名项目解决看不到原项目的问题。

## 全部项目的阅读顺序

列表按告警优先，再按最近数据更新时间排序。卡片上的颜色和项目状态并非同一个判断：分数色带默认为 ≥85 良好、60–<85 关注、<60 较低；项目告警逻辑还包含可用分数 ≤80 等条件。因此看到黄色分数但仍有告警并不矛盾。

卡片更新时间是当前环境保留数据的实际接收时间，不等于查询窗口内必然有事件。全局查询选定的 UTC 窗口由各项目按各自时区解释；跨项目比较时同时看时间标签。

## 时间、环境与链接

| 控件／行为                           | 实际含义                                   | 使用提示                                      |
| ------------------------------------ | ------------------------------------------ | --------------------------------------------- |
| 环境 `dev/staging/prod`              | 独立的数据筛选条件                         | `prod` 不包含 `dev`，也没有“自动汇总所有环境” |
| 最近 7 天／30 天／3 个月／半年／1 年 | 预设范围解析后写入链接的 `from/to`         | 阅读实际起止时间，不只读预设名字              |
| 全部项目的“自定义”                   | 输入 UTC 时间                              | 不要直接把北京时间当 UTC 填入                 |
| 项目内部的“自定义”                   | 输入项目本地时间                           | 按页面显示的时区填写，点击“应用自定义范围”    |
| 结束时间“不含”                       | 开始包含、结束不包含，即 `[from,to)`       | 恰好发生在结束时刻的事件落在下一窗口          |
| 分享、F5、浏览器前进后退             | 保留链接中的固定查询窗口                   | 适合复查旧问题，不保证把新事件纳入            |
| 质量分析中的“刷新”                   | 预设范围推进到当前时间；自定义日期保持原值 | 新触发错误后使用这个按钮，详见排障篇          |

项目内自定义范围最长 13 个本地日历月。使用有夏令时的项目时区时，重复时刻取较早瞬时，不存在的时刻向后调整；分析报告中最好保留链接里的带时区起止值。

## 看到这些状态时怎么做

| 表现                  | 意义与下一步                                   |
| --------------------- | ---------------------------------------------- |
| 待配置／未激活配置    | 请管理员确认业务目标并激活对应运营或质量版本   |
| 无数据／`no_data`     | 当前范围没有相应事实，先检查环境、时间和接入   |
| `partial`／观察值     | 只证明已收到的部分事实，不能推断完整业务量     |
| `not_collected`       | 所需事实未采集，增加时间范围不能凭空产生它     |
| 样本不足              | 保留具体分母和样本要求，等待积累或选择合理范围 |
| `stale`／保留上次数据 | 刷新尚未完成或失败，旧结果不能当最新激活版本   |
| 加载失败／403         | 重试或核对访问权限；不是业务数值为零           |
