# 04 · 指标管理与分数配置

[返回目录](README.md) · 前一篇：[页面分析](03-pages.md) · 下一篇：[设置与接入](05-settings.md)

本篇面向负责维护业务口径的管理员；只读用户可以照相同入口查定义和版本。实际写权限见 [账号角色](01-getting-started.md#账号角色与业务职责)。所有目标、阈值和示例都应由业务负责人确认适用性。

## 先分清三件事

| 内容           | 回答的问题                             | 入口                       |
| -------------- | -------------------------------------- | -------------------------- |
| 分析对象       | 哪个模块、页面、工作流算作我们的业务？ | 指标管理 → 分析对象        |
| 指标及展示绑定 | 如何算、在哪些页面显示？               | 运营指标／质量指标及其绑定 |
| 分数           | 如何把合格指标按目标、方向和权重组合？ | 分数管理                   |

配置不是采集。新增工作流、页面或指标不等于业务应用已发事件；修改展示绑定也不改变历史原始事件。运营与质量有独立的版本库类型，一个类型激活不能代替另一个。

## 新项目的配置顺序

1. 按 [设置与接入](05-settings.md) 创建项目并验证接入。
2. 在“分析对象”创建功能模块、页面及需要追踪的工作流。
3. 配合接入开发者确认页面路由、身份、业务操作、工作流实例及终态确实匹配。
4. 根据实际需要发布组织目录和全量接入声明；不需要组织分析时，不必为了让该栏目有数字而虚填。
5. 分别核对运营、质量草稿中的定义和展示绑定。
6. 确认分数模板和业务目标，校验、试算、评审后激活对应完整快照。
7. 回到概览、业务、页面分析核对版本和结果；记录仍不可用的原因。

## 配置功能模块与页面

**功能模块：** “指标管理” → “分析对象” → “功能模块” → “新建功能模块”。填写 `moduleKey`、名称和展示顺序，保存后确认列表中状态。使用稳定 key；更改业务展示名称不应随意改变接入标识。

**页面：** 切到“页面”，先选所属功能模块，再“新建页面定义”。填写“观测或模板 route”，核对“保存为”预览；route 以 `/` 开头，不包含 query 或 hash。选择名称、模板、预期使用频率、关键度及是否核心页面。

| 模板              | 常见用途             | 业务目标的思考方式                     |
| ----------------- | -------------------- | -------------------------------------- |
| 实时监测 / 驾驶舱 | 持续观察大屏         | 看可见时长、覆盖与预期使用频率         |
| 信息分析          | 检索、阅读、分析结果 | 结合访问深度和合理阅读时间             |
| 任务操作          | 提交、审批、下载等   | 结合任务完成和耗时，不追求停留越久越好 |

已有页面 route 不在编辑框里任意改写。模块、模板、使用频率、关键度和核心状态变化会创建新 revision，历史用旧生效窗口解释；界面提示“不建议频繁修改该字段”。

停用、归档和恢复都有各自入口。处理仍被页面、工作流或其他配置引用的对象时，按服务端给出的冲突原因先调整依赖；不要把“归档”理解为删除所有历史数据。查看归档对象需要启用“显示已归档”的开关。

## 配置工作流：把业务语言变成可识别的步骤

入口：“分析对象” → “工作流” → “新建工作流”。

1. 填写 `workflowKey`、名称与所属模块。
2. 选择开始策略：“首步骤自动创建匿名实例”或“显式 SDK 创建匿名实例”；与接入开发者商定实例如何开始、怎样避免串联不同任务。
3. 设置整体超时，添加并排序步骤；每步填写稳定 `stepKey`、名称和“步骤达成条件”。
4. 为 completed 指定成功终态步骤，按需要指定 failed／canceled 步骤。单个步骤达成不自动等于整个工作流成功。
5. 阅读侧边“配置说明”：主体、判定时机、填写提示和不能推断的内容。
6. 保存工作流／草稿，修正校验提示；在列表通过激活入口发布。已经激活的定义不能原地编辑，后续修改进入新草稿。
7. 在业务应用真实执行一次，再到“业务分析” → “工作流追踪”核对定义版本、阶段与实例。

| 步骤条件       | 使用前需要什么                                            | 它不能单独证明什么                    |
| -------------- | --------------------------------------------------------- | ------------------------------------- |
| 显式 SDK 上报  | 开发者在业务节点发出约定步骤事实                          | 没有上报的业务节点已完成              |
| 元素交互       | 稳定 selector 和正确交互事件                              | 点击后业务一定成功                    |
| 请求完成       | 请求路径、方法和实际采集能力                              | HTTP 技术成功等于业务成功             |
| 页面生命周期   | 已配置页面的加载完成 `loaded` 或刷新 `refreshed` 就绪事件 | 用户已看懂页面或已完成任务            |
| operation 终态 | 已登记 operation key，业务端上报成功／失败／取消          | 在配置框里写 key 就会自动产生业务结果 |

超时固定作为 `approximate_abandoned`，不是确定业务失败。复杂任务优先由开发者确认显式实例关联；不要把浏览器中的相邻操作都想当然地合成一个任务。

## 修改指标：草稿 → 校验 → 影响评审 → 激活

1. 选“运营指标”或“质量指标”，选择要基于的版本。系统默认指标的受保护 key 和语义不能任意覆盖。
2. 点击“从 v… 创建工作草稿”或“继续编辑 v… 草稿”。只在草稿中编辑；激活快照不可原地改写。
3. 使用现有表单配置业务指标、受控公式及最小样本。公式只支持受控能力，不是任意 SQL 或脚本执行器；校验失败时按依赖和语义提示修正。
4. 在运营指标中展开“概览／业务分析／页面运营展示指标（版本化）”，勾选所需指标，并“保存…展示到草稿”。最多 24 项；`partial` 可显示限制，`not_collected` 不可绑定。
5. 从旧版本升级且缺少新定义时，按需要使用“同步工作流事实定义到草稿”“同步操作效率与组织定义到草稿”“同步页面使用定义到草稿”；同步不会静默改当前 active。
6. 点击“服务端校验”“查看 diff / 影响”，检查新增、删除、变更、下游、展示位置和分数引用。
7. 点击“激活”。带分数的完整快照会转到“分数管理”做激活前检查；不带分数的快照按确认对话框校验并激活。
8. 返回消费页面刷新，确认显示的运营／质量版本正确。修改质量定义却只查看“运营”版本筛选，会漏看质量版本；在“版本库”选择“全部类型”或“质量”。

**预期：** 新版本成为该项目该类型唯一 active；旧版本变为已取代，历史快照仍在。误改时可从旧快照创建修正草稿，或按“重新激活旧快照”走检查流程；重新激活恢复的是完整快照，不只是某个数字。

保存时若出现冲突，先保留自己的输入和变更说明，刷新并重新核对当前草稿。不要通过连续点击保存覆盖别人已完成的更新。

## 分数管理的四步向导

入口：“指标管理” → “分数管理” → “运营分数”或“质量分数”。

1. 选择版本并“编辑工作草稿”或“复制为工作草稿”。
2. **模板与名称：** 确认采用的系统模板版本、名称、业务 owner、单位；模板升级需显式采用。
3. **业务配置：** 确认业务范围、目标活跃用户、预期工作日、核心页面及关键任务等页面要求的信息。业务确认不等于现场事实已完整。
4. **维度与指标：** 检查参与指标、方向、目标、权重、样本门槛。默认模板可作为起点；不要为了凑出总分降低真实业务要求。
5. **校验与预览：** 运行校验，阅读配置完整性、差异和固定示例。固定 fixture 是算法解释，不是你项目的真实表现。
6. 保存草稿，核对分数查询区自己的环境与时间；按需“保存历史试算”。没有事实时，试算不可用是正常结果。
7. 点击“激活前检查”，阅读配置与业务确认、影响、历史试算，满足条件后确认激活完整快照。

运营默认四维为使用覆盖 30%、持续使用与访问深度 25%、任务达成 30%、使用效率 15%；质量默认为 JS 稳定性 35%、资源稳定性 15%、API 稳定性 30%、页面性能 20%。**当前选择的已激活快照才是实际口径**，不能把默认比例当作所有项目永久固定值。

## 为什么有事实却没有总分

默认总分门槛包含链路健康、至少 3 个可参与维度、叶子权重覆盖至少 70%，同时还要满足所选版本、环境、样本和来源完整性等条件。

“叶子项”是最低层评分项；“可参与”表示该项数据、样本、目标等条件满足。缺失项不按 0 分处理，而是在合格项中重新归一化。查看总分时还要看缺失维度和实际贡献；同样 80 分可能来自不同覆盖，不能仅比较数字。

质量默认模板的错误率叶子要求相应分母样本 1000，页面性能 LCP／INP／CLS 叶子要求各自有效样本 100；详见版本定义。演示里触发一条 JS 错误可以查到实例，但不足以自动产生质量分数。

## 组织目录与全量接入声明

这两个面板在指标管理中使用；组织目录用于业务编制和历史归属，接入声明用于说明项目／环境／release 的实际使用采集覆盖，不能互相替代。

- 目录：按界面“导入格式”准备受控 JSON，用户引用与 SDK `setUser` 对齐；“校验并保存草稿”后核对人数、来源、有效期，再“发布此目录版本”。当前每版本最多 500 人、项目最多 100 个版本，只支持单角色；不填姓名、邮箱和原始工号。
- 声明：选择环境、实际已部署 release、有效天数和覆盖状态；核实后勾选确认，“校验并保存声明草稿”，再“发布此接入声明”。中断或已知缺失时按实际状态声明，不能标成完整。
- 两者从发布时刻向后生效，历史不回填。增加页面、变更 revision、SDK 或 release 后重新核对声明；目录变化发布新目录。界面有目录不等于事件完整。
