# 05 · 设置、接入与日常管理

[返回目录](README.md) · 前一篇：[指标与分数](04-metrics-and-scores.md) · 下一篇：[排障与交接](06-troubleshooting.md)

左侧“设置”包含“接入指南”“探针版本”“接口管理”“异常访问”；有写权限的管理员还能查看“审计”。只读账户能看的页面不代表允许修改、发送测试事件或签发凭证。

## 创建项目并准备第一次接入

**前提：** 全局管理员已登录；明确业务名称、项目时区、业务应用 Origin 和保留策略。

1. 在“全部项目”点击“新建项目”。填写名称、IANA 时区（如 `Asia/Shanghai`）、允许 Origin、数据保留天数；确认初始运营与质量模板。
2. 点击“创建项目”，进入项目后先打开“设置” → “接入指南”。新项目的两类模板是草稿，不自动激活也不自动产生分数。
3. 核对 `appId`、接收 endpoint、推荐 SDK 与固定版本 ESM 地址；点击“复制接入代码”交业务应用开发者按实际环境集成。
4. SDK 初始化中的 `appId/env/release/endpoint` 必须匹配实际应用。页面采集不包含 query；需要识别业务用户时使用可信后端提供的不透明引用。
5. 按页面 CSP 提示配置脚本与连接来源；在“项目配置与 Origin”填入真实业务来源并“保存项目配置”。
6. 在项目 Origin 白名单中同时允许当前管理站的精确 Origin，管理员再点击“发送测试事件”；平台测试同样检查来源，只有业务站白名单不一定足够。观察请求 ID 和链路状态，直到“异步入库”“可查询”证实，而不只看发送已接受。
7. 再让开发者从真实业务页面产生访问和一个可控事件；验证该业务 Origin、应用配置与对应环境也成功。平台内测试事件不能代替所有业务接入场景。

**预期：** 测试事件从发送到可查询有独立证据，真实业务事件也落在正确项目和环境。用户看到“待证实”时，保留请求 ID，再排查异步链路。

### Origin 到底填什么

Origin 是来源协议、主机和端口，例如 `https://ops.example.com` 或 `http://localhost:5173`，不含路径、query、hash 和通配符。端口不同是不同来源；将业务应用地址的一整个页面路径粘进去不能代替来源配置。

`appId` 是项目采集标识，不是管理员密码，也不是外部数据导出凭证。接口 Bearer 凭证另行签发。SDK 是业务应用显式引入并升级，保存探针策略不会向业务浏览器远程推送新代码。

## 项目配置与成员

“接入指南”下可修改项目名称、时区、事件保留天数、Origin 和采集状态，使用“保存项目配置”生效。时区影响自然日、周、月的解释；修改前与分析使用者确认影响。配置保留天数与物理存储 TTL 的关系可在概览诊断查看，不应把界面配置误认为历史数据已经全部清理或可恢复。

“项目成员”按已有注册用户 ID 添加，选择 `owner/admin/viewer` 后“保存成员”；移除前核对用户与项目。该入口管理成员关系，不创建完整的新登录账户。业务员工名册请用指标管理里的组织目录，不要把所有被监测用户都加成平台管理员。

需要安装、备份、初始化管理员或服务器操作时，使用 [Ubuntu 22.04 部署指南](../production-ubuntu-22.04.md)，由维护者操作；日常用户排障不需要重置数据库。

## 探针版本：先看观测，再配置策略

入口：“设置” → “探针版本”。

1. 按项目顶部选择环境和时间，核对实际观测版本、契约、事件数、占比及最后观测时间。
2. 区分“实际观测版本”和“已配置策略”。有升级建议不表示浏览器已升级；未知版本仍计入分母，空范围显示无数据。
3. 管理员填写探针版本、策略、Release notes 和升级建议，“保存探针策略”。
4. 使用 blocked 策略时必须明确勾选拒绝新事件；删除策略恢复未配置行为，不删除或重解释历史事实。
5. 升级业务 SDK 后再次在实际环境产生事件，观察新版本占比和最后时间。

## 外部接口：从默认关闭到受控启用

当前固定接口类型为 `metric_snapshot`、`metric_trend`、`quality_summary`、`prometheus`。这是已定义的数据接口，不是任意查询、任意 SQL 或可选字段导出器。

**前提：** 有项目写权限，明确使用方、环境、时间范围、过期时间与请求频率。

1. 打开“接口管理”，选择类型并填写允许查询起止时间、凭证过期时间、单次最长天数及每接口每分钟请求上限；环境来自当前设置上下文，保存前再次核对。
2. 创建接口后初始关闭；核对授权范围后点“启用”。
3. 保存仅此一次显示的明文凭证，并用页面显示的地址和独立 Bearer 授权调用。刷新、切换上下文后明文会清除，列表不能恢复。
4. 对照“最近调用”“最近状态”和审计核查消费方结果；`quality_summary` 如有 `nextCursor` 继续分页，其余固定接口不接受 cursor。
5. 不再使用时“停用”或“撤销”；需要更换凭证时“轮换”。旧凭证无宽限期，通知实际使用方配合更新。

日期使用带时区 ISO 格式，查询 `[from,to)`，不可越权环境、超授权范围或使用未来终点。Prometheus 也使用相同授权及绝对时间查询参数；分数不可用时通过可用性表达，不伪造为零。

“修改授权”并保存会停用接口并撤销旧凭证，必须重新启用。所有凭证共享接口分钟请求计数；停用、撤销与轮换拒绝下一次新请求，不能追回已经完成授权并正在处理的请求。

## 异常访问：规则与真实批准是两步

入口：“设置” → “异常访问”。这里用于调查，不提供个人评分或绩效排行榜。

1. 先阅读现有“调查证据”和不可计算原因。多 IP、无权限拦截在缺事实时明确不可计算，不能由设备数推导 IP 数。
2. 管理员选择规则，按界面草稿配置核对阈值、最小样本、环境、可见角色、工作时间及例外，“创建待评审草稿”。示例阈值不是业务默认批准。
3. 经真实管理层与安全评审后，按系统要求由 owner 登记批准者、时间、来源和真实性声明；不能把测试审批数据抄到真实项目。
4. 只启用已批准版本。修改规则要复制／创建新草稿并重新评审，旧批准不自动延伸。
5. 调查时同时解释共享账号、出差和值班等已批准例外及历史样本范围。需要交接时使用“导出可见调查证据（记录审计）”。

异常证据可见性还受批准版本角色范围限制；能进入项目并不意味着能查看所有命中。配置、查看、命中与导出按实现记录审计。规则审批未完成时保持关闭，不把它当作系统故障。

## 用审计追踪变更

管理员打开“审计”，按分页检查配置、接口、规则等变更和操作结果。遇到争议时，保存时间、项目、对象版本、请求 ID 及相关条目，不只凭当前界面猜测是谁改的。审计不能恢复已清除的明文凭证。
