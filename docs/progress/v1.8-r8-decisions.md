## 事务控制记录的持久化 offset

`c66e4f5c7203643f9fc4ec9cc4cea7e135999bfc` 的完整回归 run `37744075561` attempt 1 已通过全部产品、SDK、性能和三类故障恢复，但备份前对象 topic committed/end 为 31/32，严格追平门禁阻止备份。KafkaJS 2.2.4 的 Runner 会过滤事务控制记录，并在最后可见消息被 resolve 时包含隐藏尾部；显式使用最后可见 offset + 1 会覆盖这一正确边界。仅含控制记录的批次不调用应用 eachBatch，关闭 autoCommit 也会使其无法持久提交。

改为 autoCommit=true、autoCommitThreshold=1，继续 eachBatchAutoResolve=false，且仅在整个处理 slice 的 ClickHouse、MySQL 和死信写入均成功后 resolve 全部消息，再调用库的条件提交。移除提前 resolve 死信消息，防止较后 offset 越过较早的失败写入。未处理后缀不 resolve，失败会重放；readUncommitted=false 不变。锁定版本的实际 KafkaJS Batch/Runner 单元回归覆盖隐藏尾部、纯控制批次、大整数 offset、slice 后缀及混合批次写入失败。未放宽物理 offset 完全追平断言。该 SHA 的生产 Compose run `37744075585` 成功，但修复后仍需两条工作流重新验证。
