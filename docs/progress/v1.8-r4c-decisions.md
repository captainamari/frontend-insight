## 2026-10-03 C07：正式活动覆盖的信任依据（新建议，未批准）

此项不是再次确认 C01–C05，也不改变已批准的小群体策略。原始任务要求只有会改变指标结果、且已有依据无结论的部分才提出决策；本项影响正式组织使用率能否输出。

证据：`organization-facts.ts` 当前归并 page_view 和受控 operation 开始；`analytics.ts::validUsageFacts` 的历史查询则包含页面访问与成功 feature。R1-C D1 要求统一已识别、有效、已归类业务活动及完整性，不能直接复制旧 SQL 或将开始观察当成规范 UV。目录的 complete 仅证明名册。当前 ingestion/consumer 的成功只能证明已接收数据的处理，不证明所有业务入口已部署、所有客户端均送达。

反例：编制10人，已接入入口观察到5人，另一个未接入入口有3人仅在那里活动。数据库链路完全健康仍会给出5/10；按完整业务范围应为8/10。旧数据中没有证据能自动区分它与真实只有5人活跃。把现有 null 改成0.5会改变结果可信含义。

## 已有依据可直接实施

R1-B `system-metric-catalog.ts` 已规定 form_efficiency 三个分子分别为修改、重置、校验失败次数，分母均为提交尝试，minimumSample=5。重置次数/提交可能大于100%，不得截断或偷换为有重置表单占比。三个子指标不是一个标量/效率分。operation_fail_rate 分母是同一显式适配器的全部受控操作，不是仅成功加拒绝。未获知业务结果时保留 unknown，不能从异常正文或 HTTP 状态推断。

目录先交付项目/env 隔离的受权导入、校验、发布与元数据历史。单 roleId 继承现行契约；多角色不能静默选第一个，输入数组被严格拒绝。发布只能从服务端当前时间向后生效，不支持补造历史归属。用户先在业务可信边界把直接身份换成与 SDK 相同的 u_ 不透明引用；服务端复用项目 HMAC，不把原始引用写入数据库/日志/审计。部门/角色仅受控 key，无名称字段。viewer 不读目录个人行。

## C01 表单生命周期与窗口（已批准 A）

证据：§2.6.2 与 R1-B 明确分母，但没有规定未提交销毁表单、跨窗口修改如何分摊。
反例：23:59 修改5次，00:01提交一次。按事件时间分桶则前一天5/0、后一天0/1；按生命周期结算则后一天5/1。
A（推荐）：一次 trackForm 到显式 destroy/SPA离开/身份切换为一个生命周期；同 formId 重复安装复用handle；失败重试创建新提交尝试；计数在结算瞬时归桶，显示生命周期结算口径。未提交生命周期披露但不参与提交比率。销毁/导航只表示结算，不推断业务成功。
B：每次修改/提交单独事件，按事件时间归桶，跨窗口比率必须显示无提交分母与残缺生命周期。
现有实现只交付受控计数与独立结算事实，不把 A 当成已批准的正式指标定义，不改 active。

## C02 未知业务结果（已批准 A）

反例：10次受控操作，2次拒绝，3次结果未知。2/10 与2/7不同；2/10只是观测到的拒绝比例，不能把未知当成功。
A（推荐）：分母保留全部10次；明示success/rejected/technical_failure/canceled/unknown，unknown>0时正式值null，观察分子/分母仍可解释，不改变默认评分。
B：仍展示2/10但标partial，不能宣称完整业务失败率。
网络抛错默认unknown（可能已在服务端提交成功）；已解析返回值只允许受控结果类别。分类器异常不改变宿主返回值。HTTP200+rejected保持业务拒绝，不能生成api_error事实。

## C03 重复操作24h与相关会话（已批准 A）

证据：字典要求同用户同对象24h内操作≥3的相关会话占比；未固定滚动方向、命中后追溯会话或分母操作类型。
反例：A会话在t0操作一次，B在t0+23h两次；命中时只计B或连A共两会话会产生不同结果。午夜切分会遗漏合法重复。
A（推荐）：同项目/env/用户/对象类型/引用/受控operationKey，按去重开始实例；每个开始t看[t-24h,t]（精确24h端点包含），达到3时该组窗口涉及的会话均命中。分母为查询窗内有纳入操作的去重用户+session，分子为这些会话中截至asOf可证明命中者。查询需前后24h事实，未来尚未观察完整时partial；迟到重放受event time与receivedAt双asOf限制，不混自然日。
B：只将第三次及后续操作所在会话计为命中，窗口回溯24h；指标解释与A不同。
C03 A已批准；正式重复率仍需真实采集与完整性验证后开放。

## C04 对象引用隐私边界（已批准 A 及48小时保留边界）

A（推荐）：宿主可信业务后端处理原始对象ID；按project/env/objectType与短期密钥HMAC，浏览器只获得不透明引用。相邻密钥重叠至少24h+准入迟到期并保留受控桥接；关联键仅内部查询，不返回API/UI/日志。平台不新建接收原始业务ID的事件或公开tokenization接口，不向浏览器给秘密。需确定可信后端部署、密钥生命周期、允许迟到上限及物理保留期，再实现/验证轮换。
B：宿主提供短期随机映射，可信后端持有原始映射并销毁；平台仅收随机引用，需要同样的跨窗口连续性证明。
公共盐hash不满足要求。现有SDK/API均不接收bizRef或原始对象ID。

## C05 小群体与反推（已批准 A 及固定闭合桶限制）

证据：需求与计划要求最小人数，但没有数值；目录minimumSample不等于隐私阈值。
反例：总计10减公开部门9，泄露被遮盖部门1；单独抑制卡片仍可能由比率/时长/TopN反推。
A（推荐）：版本化k=5，检查eligible人数与实际贡献人数；任一分组不足时同一结果族（总计/分组/比率/时长/排名/趋势）整体抑制；只提供固定项目日历桶和固定目录分段，不开放任意部门×角色交叉/个人筛选。相邻自定义窗口仍可能泄露，应在发布前确定固定可发布窗口或更严格查询约束。
B：k=10，维持相同全族抑制与查询约束，更多小团队无数据。
C05 A及下述固定闭合桶限制已于2026-09-29批准。当前服务端已实现k=5全族抑制；正式活动覆盖未完成，组织正式value保持null，兼容且未被抑制的观察结果单独披露。目录管理可正常录入、发布。

## C06 跨目录版本

推荐按真实目录有效区间分段，分别用该版本eligible人数；不给跨版本单一人数比率，不用最新目录重解释过去。例：5人→10人，两段活跃3和4，不能用7/10（可能重复）或简单平均比率。若要求跨版本单一值，需要另行批准成员并集或人时加权语义。当前目录底层支持时态查找，正式跨版本汇总仍待该规则确认。

补充已核实的保留边界：contract当前ingestion允许event time相对接收时刻最多±24小时（`CONTRACT_LIMITS.maximumClockSkewMs`），既有CH物理TTL为received_at+90天。C04不能把90天raw_events保留静默套在短期对象引用上，也不能仅删除HMAC密钥便宣称库内稳定引用消失。可信后端方案至少需要覆盖24h统计窗+既有24h准入迟到，即48h边界连续性；还要覆盖已接收Kafka积压与重放。引用专用短期存储/销毁、窗口结算后保留的非对象明细结果、旧asOf可重算能力之间的取舍已按下段建议批准；当前尚未接通采集对象引用，因此不存在先收原始ID再脱敏或未评审长期保存。

C04已批准的具体折中：采用宿主可信后端生成的项目/env/对象类型隔离引用，采用短期专用通道与存储，引用数据从接收起48小时后销毁；轮换连续性覆盖24小时统计窗与24小时准入迟到。普通90天raw_events只保存随机operation关联与受控结果，不落对象引用；短期Kafka通道同样48小时，死信仅安全原因与消息摘要。超期积压/重放明确返回覆盖不足，不偷偷延长引用保留。长期仅保留不含对象引用的会话命中事实、封存聚合及版本/asOf证据；不承诺引用销毁后任意引用级重算。若业务必须完整重放，备选是经单独批准延长短期存储期限，不能以现有90天TTL作为授权。此处48小时保留取舍已批准；短期通道/存储及封存仍未交付。已实现可信后端签名引用原语、验证和轮换别名到滚动窗口计算的内存桥接；不等同于真实链路完成。

C05已批准的发布限制：k=5（备选10），同时检查eligible与实际贡献人数；仅发布已闭合且迟到期结束的项目日历日/周/月桶，不发布任意滑动from/to组织数值，不提供部门×角色交叉筛选。任一受保护分组不足时连同总计、比例、时长、排名与趋势整个结果族抑制，避免总计减分组直接反推。原业务分析公共时间选择仍保留，不兼容组织发布窗口时明确不可用，不静默改范围。阈值与这些限制已经一起批准，采用内置策略，不增加配置审批。

## 2026-09-30 C04落地补充

继续实施已批准范围，无新用户批准记录。可信后端provider从项目授权接口获取当天及前3个UTC epoch密钥，按UTC日期刷新；UTC仅用于密钥轮换，指标仍是滚动24h。浏览器只拿签名引用，不拿密钥；有浏览器Origin/Fetch Metadata的密钥请求拒绝。业务结果与引用在Kafka同一事务发布，避免单边成功。短引用表48h逻辑截止，长期仅无引用见证；接收或投影缺失必须不可用。

部署限制如实记录：Kafka retention和CH TTL都是后台物理清理，不能保证停机/繁忙时恰好48小时物理擦除。已设置短topic retention与segment、CH TTL merge参数；查询及消费者严格拒绝过期引用。若要求硬实时物理擦除，当前实现不满足，应单列为部署阻断，不能借内部使用默认为已批准延长保留。
