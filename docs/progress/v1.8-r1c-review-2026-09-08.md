## 1. 运营口径：逐项问答

### Q01｜旧 line 21、36：没有匿名业务用户，还需要 deviceId 兜底吗？

**问题**：缺兜底会使人数偏小吗？本系统要求登录，未登录不能使用功能，应排除；同时认同统一规范 UV。

**解答**：只有确实存在应纳入统计的匿名业务活动时，旧账号去重才会因此少计。80 个账号加 20 个设备不自动等于 100 个真实人，设备与账号还可能重叠。旧示例仅用于说明两种纳入范围的数值差异，不适合作为本系统的运营目标人数依据。登录页访问、探测和测试流量不能靠 deviceId 变成有效业务用户。

**确认与方案**：本内部系统运营统计排除未登录业务活动。保留平台规范 UV 的统一身份规则（已识别 userId，允许匿名的范围才按 deviceId 兜底），在指标查询之前统一限定“已识别的有效业务活动”范围。所有相关 UV 派生项引用同一范围内的规范 UV，不新增账号 UV 别名，不在不同公式内各写过滤规则。原子总体 UV 与业务范围 UV 可以因筛选不同而不同，界面必须标明范围，不能都无说明地标成同一个数。

过滤范围及身份规则引用须随版本固定。`userId` 缺失也可能是 SDK 接入遗漏，不能直接断言用户未登录；披露未识别/排除样本及接入异常，无法证明范围与采集完整时返回不可用原因，不悄悄缩小分母制造高分。不得仅凭这次评审新增登录状态采集字段或跨设备身份合并算法。

### Q02｜旧 line 22：核心页面覆盖，为什么还要固定环境与版本？

**问题**：是否判断关键页面被访问，并防止环境或配置变更影响可比性？

**解答**：是。公式仍为“被访问核心页面的关键度权重之和 / 全部启用核心页面关键度权重之和”，每页按同范围 `pv > 0` 判定。例如页面权重 2、1，只访问第一项，覆盖率为 2/3。这个指标只证明发生了页面访问，不能证明用户阅读理解、页面渲染成功或任务完成。

**确认方案**：固定核心页面集合、关键度、页面 revision、指标/分数版本、业务活动范围、env 和时间窗口。同配置在 prod/staging 得分不同本来就可能合理；要避免的是混合两者或拿不同版本结果当成可直接比较。解释页列出访问/未访问页面、PV、权重和当前版本。

### Q03｜旧 line 23：活跃日覆盖是否应由配置驱动并展示？

**问题**：应活跃日期中实际有活动的天数，需要让使用者看得懂。

**解答**：理解正确，但旧代码并非完全写死：`analytics.ts::expectedLocalDates` 已读取 `settings.expectedActiveWeekdays` 与查询 timezone。缺口在于这些设置和有效活动口径尚未完整冻结在评分依赖快照中，而非必须新建一个预测模型。

**确认方案**：复用已有预期星期配置；固定项目时区、查询范围和配置 revision，展示展开后的预期日期、实际活跃日期、分子/分母及排除原因。例如应活跃 5 天、其中 3 天有活动，结果 3/5。分母为 0 时不可用。此轮不新增节假日服务或自动预测工作日；查询边界当天是否按完整工作日纳入，需要在后续范围规则中明确，不能隐式改变。

### Q04｜旧 line 24：跨日持续使用率等于 Day 0 留存吗？

**问题**：起始日活跃用户后续仍活跃的比例，分母是否应为 Day 0 活跃 UV？认同所有指标统一身份规则。

**解答**：统一身份规则已确认；但两个公式回答不同问题。需求 §18.3.2 当前公式是“查询窗口内至少在两个项目本地日期活跃的用户数 / 同窗口 UV”，不固定 Day 0 人群。D1 留存则是“Day 0 与 Day 1 都活跃的用户数 / Day 0 UV”。

例：第一天 A/B 活跃，第二天 A/C 活跃。当前跨日持续使用率为 1/3；次日留存率为 1/2。不能只替换分母，否则分子可能包含 Day 0 之外的用户。也不能直接保留原 target=0.5，把不同指标当成同一评分叶子。

**待澄清方案**：建议本次保留已批准的窗口跨日持续使用公式，并在页面解释；如果希望改为 cohort 留存，需要一起确认起始人群、D1/D7 或后续任一天、观察窗完整性、评分目标及新版本。当前不把用户在概念混淆下提出的“比如 Day 0”记为完整留存公式批准，不提前开发留存模块。单日窗口无法观察跨日持续，不得输出 0 来惩罚项目；其可用窗口/样本规则需在实现前明确。

### Q05｜旧 line 25：会话深度是否应该按一天计算？

**问题**：单会话不同页面数 P50，希望时间口径清楚，倾向“一天内”。

**解答**：P50 是分布中位位置；样本单位是会话，不是用户，一个用户可产生多个会话。需求 §2.4 已规定 30 分钟无操作切分 session，所以并非会话定义完全空白。“按天查询/展示”与“一天算一个会话”不同。

例：同一人上午看 2 页，超过 30 分钟后下午看 4 页，这是两个会话。一天可以展示这两个会话的深度分布；若把一天合成一次，会话数、深度和跳出率都会变义。跨日 session 的纳入/截取策略仍需有明确查询规则，不能默认午夜重建 session。

**待澄清方案**：推荐“一天”为查询范围或趋势桶，保留 30 分钟 idle 会话边界；窗口总 P50从会话样本重新计算，不平均每日 P50。请确认你的“一天内”是否指这种展示方式。界面显示时间范围、时区、会话切分、样本单位及分位数算法。

### Q06｜旧 line 26、38、42：未归类页面及样本是否排除和披露？

**确认**：未归类页面不进入模块和分数；单会话模块数中，纯未归类会话不进入 P50 样本。混合会话只统计已归类模块，不因包含未归类页面丢弃整个会话。基础诊断仍可查看未归类页面。

**实施解释要求**：展示总样本、有效样本、排除样本及原因。例如模块计数 `[0,0,0,2,2]`，总会话 5、纯未归类排除 3、参与 2、P50=2。不能隐藏只剩两个样本的事实，仍需检查 minimum sample。

### Q07｜旧 line 27、37：workflow instance 是否要求重做交互、给每个节点加权？

**问题**：任务需要实例跟踪；是否统计每个叶子节点，并增加节点权重录入？

**解答**：一次 operation 成功只说明一个操作完成，不一定代表整项任务成功。工作流实例负责把同一次任务的开始、步骤和终态关联起来。需求 §7.3、§11 与 §18.4 已设计该模型，R1-A 也已有步骤配置；缺的是 R4-B 的正式运行时关联和事实能力，无需推翻已验收交互。

下载任务中，“请求已接受”不等于“传输完成”。任务成功率按工作流可靠成功终态 / 开始实例计算；各步骤到达率和耗时用于定位卡在哪。不能因为收到了最后一步，就推断未观测步骤都已到达；也不能默认把步骤观测缺失等同业务任务失败，应按既定终态/序列校验规则解释。

三个权重对象必须区分：评分叶子权重（如成功率在任务达成维度占70%）、任务类型权重（不同工作流的重要程度）、步骤权重（每个步骤的完成价值）。当前前两者已有模型，第三者会新增“部分完成度”指标；完成多个轻步骤不能抵消关键任务失败。

**方案**：把用户提出的“节点权重”记录为待澄清需求。若指不同任务的重要性，使用评分配置中的任务类型权重，置于高级设置；若确实要步骤部分得分，需另行确定业务意义、公式、gate 和版本，不在当前任务成功率里加入。R1-C 复用工作流定义与版本引用、接入状态说明；本次文档不授权提前实施 R4-B 或修改 R1-A。

### Q08｜旧 line 29、39：池化加权 P50 的业务意义是什么？

**问题**：希望用整项成功任务的耗时，倾向池化加权，是否相当于随机抽前50%的数据？

**解答**：不是抽样，更不是随机取一半。将全部有效成功实例按耗时从小到大排列，给每个实例赋其任务类型权重，取累计权重首次达到总权重50%的耗时。表达“按业务重要性加权后，有至少一半成功任务的耗时不超过这个值”。不是精确的“一半用户感受”：高频用户/任务会贡献更多实例，类型权重也改变影响力。

固定例：A 权重1，耗时10、100秒；B 权重2，耗时60秒。排序后累计权重为 1、3、4，50%阈值为2，故 pooled weighted P50=60秒。先算各类型 nearest-rank P50 得到 A=10、B=60，再按类型权重平均为43.3333秒；后者是类型代表值的综合，不是整体任务实例的P50，高频任务不会因更多实例获得同样的额外影响。

**已确认方案**：采用池化加权 nearest-rank P50；单位统一，任务类型权重随版本固定。明细保留按任务类型的样本和 P50/P90，避免把耗时特性不同的任务仅用一个总数字比较。既有单操作事实不能代替成功工作流实例；这次批准算法，不代表 R4-B 事实已交付。

### Q09｜旧 line 30：核心页面时长符合度为什么还要版本化？

**解答与确认**：理解正确。有效可见停留时长与页面模板目标比较，再按核心页面关键度加权；“越久越好”不成立，大屏与快速操作页目标不同。固定页面模板目标、关键度、样本门槛、leave 覆盖规则和 revision，展示原始时长/单位/目标区间/有效与缺失样本/得分。沿用已有配置入口，版本快照引用它们；不另建第二个模板管理中心。旧样本≥5和 coverage≥0.5的存在性本身不等于批准新增模板参数。

### Q10｜旧 line 40：贡献修复是不是为了避免归一化掩盖问题？

**解答**：原问题是算术解释错误：缺项后总分按可参与维度重新分配权重，旧贡献却仍乘原权重。fixture 总分82.5294，但旧维度贡献合计70.15、叶子贡献合计59.65；新的实际贡献都应合计82.5294。

标准化到0–100与缺项后重新分配权重是不同操作。总分确实可能掩盖局部严重问题，所以原始值、缺失原因、低分维度和诊断都要可见，但此次不是新增告警规则或放弃总分。已实现的贡献修复保留；后续UI必须数表一致、能看出哪些项缺失。

## 2. 质量、透明性和默认模板

### Q11｜旧 line 50、60：JS rate 为 partial，是因为怎么算、算谁、在哪算未统一吗？

**解答**：方向正确。已有 JS 错误分子和 PV，并不等于规范 `js_error_rate` 的版本化查询已交付。“怎么算”=次数/PV；“算谁”=明确统计对象、身份及纳入范围；“在哪算”=同项目/env/时间/版本的服务端查询。还需“数据从哪来、够不够”。JS 次数/PV不是错误用户比例；可以大于100%。API 和资源分别用各自请求总数，不能套用 PV。

**已确认 D2**：保持 JS/Web Vitals 等 partial；API/resource rate 缺真实总分母和规范查询，保持 not_collected。计划 §10.2 改为按实际事实与查询能力区分，不改代码标签凑验收。待后续证据满足才提升状态。

**已确认透明性要求**：统一在现有指标详情提供业务问题、公式、分子/分母、单位、去重与人群范围、事实来源/上报时机、项目/env、时间窗口/时区/粒度、分位数、目标、有效/排除样本、最低样本与缺失策略、版本、生效时间、owner、实施状态及原因。卡片先显示结果、范围、样本、状态；详细规则在解释抽屉展开，普通用户无需通读算法才能使用。元数据不完备不代表要人工给每次查询补资料；复用同一指标定义生成说明。
