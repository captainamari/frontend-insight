## 查询预算与性能

环境：GitHub `ubuntu-24.04`、Linux x64、4 vCPU、16,766,414,848 bytes RAM；Node 24.21.0、pnpm 11.15.1；真实 MySQL 8.4、Kafka 4.1.1、ClickHouse 25.8 镜像系列。下面均来自最终 R7 提交，p95 使用 nearest-rank。

| 采样对象                     | 预热/有效样本 | p95      | CH 查询数       | 最后样本扫描行 |
| ---------------------------- | ------------- | -------- | --------------- | -------------- |
| R7 probe-versions / Chromium | 5 / 20        | 15.50 ms | 1               | 396            |
| R7 probe-versions / WebKit   | 5 / 20        | 23.52 ms | 1               | 407            |
| R6 页面组合查询 / Chromium   | 5 / 20        | 46.43 ms | 3（运营事实 1） | 1089           |
| R6 页面组合查询 / WebKit     | 5 / 20        | 42.32 ms | 3（运营事实 1） | 1155           |
| R5-A 质量查询                | 3 / 20        | 59.83 ms | 1               | 3607           |

R5-A 按 20 events/s×60 秒、200 events/s×10 秒发送并接收 3200 事件；接收 HTTP p95=57.79 ms。这是 100 批响应（60 批 20 事件、40 批 50 事件；脚本无独立预热）的接收耗时，不是异步入库延迟。质量分母实际为 640 API 请求、1280 资源请求。

R7 事实读取上限：50,000 返回事件、1,000,000 扫描行、256 MiB、5 秒；超出时明确失败。探针元数据读取固定为 admin 5 次/viewer 4 次（源码路径核对，不含共享鉴权 guard）；不随版本/事件数量增长。异常调查合并窗口和最大基线一次读取，按规则记录命中审计。详细 bytesRead/elapsed 见证据索引。

这些是小规模 CI 样本，不是生产容量保证。两实例限流验证的是同库、同测试环境下独立连接池，不声称完成多主机故障/时钟偏移测试。授权不缓存，已开始处理的请求不宣称可追回。外部读模型沿用本轮既有读模型性能回归，未设独立生产容量 SLO。
