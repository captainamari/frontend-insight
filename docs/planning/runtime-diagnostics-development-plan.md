## 1. 用户决定与执行目标

Jesse 于 2026-10-10 明确要求：“不需要脱敏，只要是有价值的诊断信息都收集了。但是可以考虑展示时什么角色的用户能看到。”本计划据此采用 **诊断原文保留、访问按项目和能力授权**，不再用固定文案、字符串替换或去掉 URL 参数代替有价值的错误事实。详见 [ADR-021](../adr/ADR-021-runtime-diagnostics-and-access.md)。

目标：工程师从一个错误实例回答“什么错误、哪个版本和代码位置、之前做了什么、哪个请求或操作失败、有哪些关联日志”，并能复制证据定位。普通查看者继续使用质量统计。既有指标公式、真实分母、项目/环境隔离不重做。

此次授权是编制并提交后续开发计划。用户合并后，按 D0 → D1 → D2 → D3 → D4 → D5 → D6 → D7 顺序实施；不把本次文档合并当作全部代码已完成。

## 3. 功能范围与采集方式

| 内容 | 计划行为 | 呈现方式 |
| --- | --- | --- |
| Error | 原始 name/message/stack、cause 链、AggregateError 子错误、异常来源（全局/Promise/显式/Vue/React） | 原文和结构化帧并列；保留换行、函数、文件、行列号 |
| console | 包装业务页面自身 `error/warn/log/info/debug`，记录时间、级别、参数快照；默认 error/warn，其他级别可配置 | 随异常附上之前的环形缓冲；console 单独记录不直接计为 JS 异常 |
| 请求 | 请求方法、完整 URL/query、开始/结束时间、状态、失败原因、耗时、请求关联 ID；失败请求的文本/JSON headers、request/response body | 网络详情与异常时间线关联；成功请求默认保留元数据，正文按路由配置 |
| 页面与运行环境 | 页面 URL、route、release/build、浏览器/OS/UA、视口、在线状态、导航和生命周期 | 错误发生时快照，不能拿查询时状态替代 |
| 操作与工作流 | 最近导航、点击目标标识、明确的业务 action、operation/workflow instance/step、应用显式提供的业务上下文 | 时间线；允许配置有意义的目标标签和上下文字段，不自动猜测关联 |
| 源码 | 与 project/release/build/asset 匹配的 SourceMap、原始文件/函数/行列号及源码片段 | 原始编译栈始终可见，映射结果作为另一视图 |
| 工程协作 | 实例链接、错误组、版本比较、复制与导出、关联 request/trace ID | 所有原文入口复用相同权限；链接不承载凭据或原文 |

采集范围围绕应用运行诊断：不为此主动遍历 cookie/localStorage、密码框或所有 DOM，不做整页录屏、不扫描其他标签页。接入方已提供的错误、console 参数和选定请求内容按原文保留，不再做内容脱敏。超限裁剪、不可序列化、浏览器不可访问是技术状态，必须明确标记，不能伪装完整采集。

浏览器内置警告、扩展隔离世界、跨域不可读响应等不等于应用 console；不能承诺页面 SDK 复制整个 DevTools。可获得的 source 信息用于分类，缺来源时显示 unknown，不能猜测为扩展或业务代码。二进制/流式响应首版记录类型、长度和不可读取原因，不为了采集消费业务响应流。

## 4. 数据与权限设计

### 4.1 两种数据用途

保留现有 `raw_events` 中服务指标计算的规范字段、错误统计和聚类投影；增加按 `projectId + eventId` 关联的版本化诊断证据。诊断原文不因聚类归一化而改写。完整 URL 与规范 `pageRoute` 分别保存；聚类使用派生 signature，不覆盖原始 message/stack。

D0 冻结诊断信封 `diagnosticVersion`、内容类型、来源、采集策略版本、截断状态、关联 ID 和 payload 上限。已有 contract v3 优先增加可选诊断扩展；若当前生成器或校验不能安全兼容，明确版本升级及 SDK/API/consumer 发布顺序，不能让新 SDK 数据静默拒收。SDK 的公共 appId 不因此获得任何读取权限。

建议采用受限 ClickHouse 诊断明细表保存错误、日志、请求及上下文；MySQL 保存能力授权、策略、审计和 SourceMap 元数据；SourceMap 文件使用服务端受限持久存储。不要把大正文复制到每一条普通事件、访问日志、Prometheus 标签或默认列表响应。实例详情按需读取；写入失败显式表现为详情延迟/失败，不能因重试重复计算错误次数。

### 4.2 建议执行的权限默认值

以下是新功能实施默认方案，不是当前已有能力。保留现有 global admin/viewer 与项目成员模型，不新建一套互相独立的“研发角色”体系。

| 用户/入口 | 质量聚合和基础列表 | 原始错误/console/请求/源码详情 | 原文导出 | 修改采集策略/诊断授权 |
| --- | --- | --- | --- | --- |
| 平台 admin | 按现有管理权限 | 允许并审计 | 允许并审计 | 允许，复用现有设置写权限 |
| 获项目诊断授权的成员（可仍是 viewer） | 仅授权项目 | 有 `diagnostics.read` 才允许 | 另需 `diagnostics.export` 且具备 read | 不随 read 自动获得写权限 |
| 普通项目 viewer | 允许 | 不允许，显示“无诊断详情权限” | 不允许 | 不允许 |
| 无项目权限/未登录 | 不允许 | 不允许 | 不允许 | 不允许 |
| 现有外部接口 token | 按原有 scope | 默认不开放诊断原文 | 不允许 | 不允许 |

服务端先确认项目访问，再计算能力；非平台 admin 必须是当前项目成员且有显式授权。撤销成员或能力后立即失效，不凭缓存中的旧角色放行。列表不得夹带原文消息、完整 URL、栈、console 等，再仅靠前端隐藏；详情、搜索摘要、下载、SourceMap 文件和导出统一执行权限。普通列表保留计数、时间、规范路径、标准错误类别等已有摘要。

读取和导出审计记录操作者、项目、实例/错误组、行为、时间及结果，不复制原文正文。详情响应禁止共享缓存；前端以文本/code 呈现原始内容，不执行其中 HTML/脚本。

### 4.3 建议初始容量值（D0 落合同，D7 实测校准）

- 单个诊断信封 64 KiB UTF-8；栈最多 32 帧/16 KiB；cause 最深 4 层。
- console 环形缓冲最多 50 条且总计 24 KiB、回溯 60 秒；单条参数最多 2 KiB，保留级别和时间。对象有深度/循环引用限制，不调用 getter，不改变原 console 行为。
- 请求/响应正文各最多 16 KiB，headers 各最多 4 KiB；仍受总信封预算约束。总量不足时优先保留错误消息/栈、失败请求，再保留最近的日志；记录实际省略项和字节数。
- 每页面实例每分钟最多 20 个完整诊断信封；基础错误计数另计，不能把详情限流误当成零错误。重复错误保留首例、后续代表样本和 suppressed 计数。
- 原始诊断默认保留 14 天，项目可设 1–90 天；派生统计沿用原政策。策略变更不回填此前未采集或被裁剪的信息。

这些上限用于宿主性能和存储预算，不做内容替换。D0 须核对实际 ingestion、代理、Kafka、客户端 batch 限制，拆批和超限结果显式化；实施时调整数值须写入决策记录及负载证据。

## 6. 分支、合并与接力规范

1. 用户合并当前 R8 后，执行者先核对实际合入的目标分支与 SHA，不假定目标一定是 main 或 refactor，也不继续从过期的 R8 head 起步。读取用户明确指定的本批范围。
2. 每批建议分支 `agent/runtime-diagnostics-d0-contract-access`、`agent/runtime-diagnostics-d1-errors`，后续按编号和主题类推；Draft PR 指向经核实的目标分支。不得自动合并或连接生产。
3. 每批维护 `docs/progress/runtime-diagnostics-results.md` 与 `runtime-diagnostics-decisions.md`，首批创建，之后追加；记录工作包/验收项、实现位置、测试命令与结果、代码 SHA、证据、剩余问题和下一批入口。
4. 默认每批合并后再从最新目标分支开始下一批。D0 完成权限与原文链路、D1 完成可定位的错误，是首个可试用交付；D2–D6 按顺序补齐，D7 才宣布全路线完成。
5. 新增迁移不改已应用文件，不用 reset/seed 替代升级；已丢失的历史消息/帧不伪造回填。原有 R6/R7 业务批准及个人行为分析边界不由本计划自动解除。

可直接用作下一批任务说明：

> 在 captainamari/frontend-insight 实施本计划 D0。先核对 R8 已合并后的实际目标分支、最新 SHA 与仓库指令，创建 D0 分支，读取本计划和 ADR-021。完成诊断合同、增量存储、项目诊断权限、受限原文读写及真实验证，维护 results/decisions，提交并创建指向目标分支的 Draft PR。不提前实施 D1–D6 的完整 UI/collector；不自动合并或操作生产。用户已明确要求诊断信息不脱敏，不再因旧字符串禁止规则阻断该诊断字段；同时不得全局关闭结构、大小、项目或权限校验。每项以本计划完成标准交付，不止提交表结构和文档。

## 7. 历史测试与旧文档如何处理

既有隐私测试不能整套删除。按用途分拆：诊断字段新增“原文一致性”正向测试；项目隔离、角色访问、默认摘要、服务运行日志和非诊断字段继续负向验证。更新原有仅允许脱敏值的 fixture 和 golden 时逐项记录新决定与预期差异，不把任意断言失败都改为通过。

[需求 v1.8](../product/requirements-v1.8.md) §8.2/§13 与 §16、[主计划](mvp-plan-v1.5.md) §16–17 的历史诊断限制由 ADR-021 在本扩展内覆盖；既有指标定义、外部 token hash/scope、Prometheus 低基数、组织指标与工作流统计合同不变。计划合并不代表当前运行版本已停止脱敏或已具有诊断权限。
