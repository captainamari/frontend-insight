## 0. 文档定位与事实优先级

v1.8 是一次面向当前 `main` 实现的产品重构，不是对 v1.7 的修订。发生冲突时按以下顺序处理：

1. 《内部业务操作系统 · 前端监测指标字典》v1.0 对字段名、事件名、指标 key、计算口径和上报时机的定义；

3. 2026-08-18 附件中的业务目标、页面名称和页面意图；
4. `main` 的真实代码、数据能力和安全边界；
5. v1.6/v1.3 中仍被本文保留的权限、隐私和工程原则；
6. 其他历史文档仅用于追溯，不构成验收条件。

`requirements-v1.7.md` 曾将附件中的 `appId`、`env`、`release`、`event`、`timestamp`、`pageRoute`、`userId`、`deviceId`、`vv`、`uv` 等改写为当前实现使用的其他名称。该决策随 v1.7 一并废弃。本版以附件名称为准，不再以“沿用现有代码”为理由反向修改指标字典。

当前项目仍处于开发阶段，未正式上线，也没有需要保留的生产数据。因此本轮重构采用 **Pre-1.0 重置策略**：

- 可以删除被新信息架构替代的路由、接口、字段和兼容分支；

## 1. 本版决策摘要

1. 登录后先进入“全部项目”入口页，不再默认进入“功能采用”。
2. 产品由 6 个一级模块组成：入口页，以及项目内的项目概览、业务分析、页面分析、指标管理、设置。
3. 项目内页面统一采用“左侧项目导航 + 右侧正文”的框架；项目级公共时间筛选位于正文顶部。
4. 原“功能采用、运营概览、页面访问、项目运营指数、前端可观测性、项目与接入”不再作为并列一级导航，而是重组进新的 5 个项目模块。
5. “项目运营指数”在 UI 中改称“运营分数”，继续复用已经实现的可解释四维评分能力。
6. 新增“质量分数”。错误和性能不再只停留在独立证据页，而是通过独立版本、独立公式进入质量评分；不得改写运营分数的语义。
7. 指标管理成为所有分析页的单一配置和语义来源，统一管理分析对象、运营指标、质量指标、分数组合和版本库。
8. 指标面向用户分为“原子指标”和“业务指标”。内部仍可保留 fact/atomic/derived/composite 分层。
9. 用户可以基于受控指标和受控运算符创建业务指标与分数，但不能提交任意 SQL、任意字段、任意 group by 或任意代码。
10. 指标启用、停用或修改必须先形成新的草稿版本；激活后版本不可原地编辑，版本是当时指标配置的完整快照。
11. 业务分析以“功能模块”为聚合单位；UI 使用“功能模块”，代码和接口使用 `moduleId/moduleKey`，不再引入 business domain/业务域作为同义概念。
12. 现有单次 operation 生命周期扩展为可选的多阶段工作流追踪；核心 SDK 继续使用显式语义事件，不默认抓取任意 DOM。
13. 页面分析默认打开“质量分析”，并可切换到“运营分析”。
14. 设置页包含接入指南、探针版本管理和接口管理；第三方接口默认关闭并使用独立的受限凭证。
15. 重构按页面或模块分批交付，每一批独立自动化验证、手工验收并合入后再开始下一批。
16. SDK、事件契约、API、MetricCatalog、数据库语义列、UI 和测试统一使用附件规范名；物理数据库列允许 snake_case 映射，但不得形成第二套业务术语。
17. 规范指标 key 固定使用附件中的 snake_case，例如 `pv`、`uv`、`vv`、`module_penetration`、`task_duration`、`js_error_rate`；当前 `page_views`、`active_accounts`、`sessions` 等只能出现在重构差异说明和删除测试中。

### 2.3 已确认缺口

- 登录后没有项目资产入口页；
- 全局时间范围只有 24 小时、7 天和 30 天，缺少 3 个月、半年和 1 年；
- 运营分数和质量证据分离，尚无质量分数；
- 指标目录固定在代码中，尚无受控业务指标公式编辑器和完整指标版本库；
- module 只有概览聚合，尚无独立业务分析页和功能模块趋势；
- operation 只有开始/终态，不能表达附件中的多阶段工作流；
- 页面质量分析以错误组汇总为主，尚无附件要求的路径/时间/类别/复现条件筛选与明细；
- 项目与接入页尚未覆盖探针版本策略和第三方接口启停管理。

### 2.4 `main` 命名审计与唯一规范名

以下差异来自 `main` @ `a79fa5368b806c9808242eb65c6d076d5d1464eb` 的事件 schema、SDK、ClickHouse raw table、MetricCatalog、API DTO、路由和页面代码。右列是 v1.8 唯一允许的新名称。

| 层级 | 当前 `main` | v1.8 唯一规范名 | 处理规则 |
| --- | --- | --- | --- |
| 应用维度 | `projectKey`；内部 `projectId` | `appId` | SDK/ingest/事件和面向接入方的 API 使用 `appId`；内部关系主键可保留 `projectId`，但不得代替事件维度 |
| 环境 | `deploymentEnvironment`，且只在可观测 payload 中出现 | `env`：`prod/staging/dev` | 所有事件必带；看板默认 `prod` |
| 发布版本 | `releaseVersion`，且只在可观测 payload 中出现 | `release` | 所有事件必带，由构建/接入配置注入 |
| 事件类型 | `eventName` | `event` | 只使用 `page_view/page_leave/performance/api/error/custom`；具体自定义动作放入 `payload.name` |
| 事件时间 | `eventTime` ISO string | `timestamp` epoch milliseconds | 服务端另存 `receivedAt`，不得覆盖客户端时间 |
| 页面 URL | 未采集 | `pageUrl` | 保留该字段名；值按 13.1 脱敏，默认移除 query/hash 中非白名单内容 |
| 页面聚合键 | `route`、`normalizedRoute` | `pageRoute` | SPA 归一化路由，是页面聚合主键 |
| 用户 | `accountRef` → `accountId` | `userId` | SDK 字段名为 `userId`；持久化前项目级不可逆处理，未登录值使用匿名标识并按 `deviceId` 兜底 |
| 组织 | 无通用事件字段 | `deptId`、`roleId` | 优先由受治理目录在服务端补充；禁止上传姓名等直接标识 |
| 设备 | `visitorId` | `deviceId` | 浏览器生成的稳定匿名标识，不宣称是真实硬件指纹 |
| 终端 | `browserFamily/osFamily/viewportBucket`，只在可观测事件中 | `ua`、`os`、`browser` | 所有事件使用同一字段；值执行白名单、长度和隐私限制 |
| 会话 | `sessionId` | `sessionId` | 保留；30 分钟无操作重新生成 |
| 业务载荷 | `properties` | `payload` | 按事件类型使用受控 schema，禁止任意嵌套对象 |
| 页面浏览量 | `page_views`、`pageViews`、部分 DTO 的 `pv` | `pv` | MetricCatalog、API、趋势、UI 绑定和 fixture 全部统一 |
| 活跃用户 | `active_accounts`、`active_browsers`、`visitors` | `uv` | 以 `userId` 去重，未登录按 `deviceId` 兜底；账号/设备拆分只可作为附加诊断指标 |
| 会话数 | `sessions` | `vv` | UI 显示“会话数（VV）”，不得只显示含义不明的 VV |
| 运营评分 | `project_operational_index`、项目运营指数 | `operational_score`、运营分数 | 公式可复用，key、API 和 UI 同步重命名 |
| 质量评分 | 尚无 | `quality_score`、质量分数 | 与运营分数独立定义和版本 |
| 分组实体 | module 与新增设计中的 business domain 混用 | `moduleId/moduleKey`、功能模块 | 复用当前 module 模型，不新建同义 business domain 模型 |

允许保留的技术字段仅用于可靠性和追踪，例如 `schemaVersion`、`eventId`、`pageViewId`、`receivedAt`、`requestId`、SDK 名称/版本。这些扩展不得替代上表中的规范业务字段。

### 2.5 v1.8 事件模型

规范事件结构如下；batch envelope 可以补充批次发送时间和 SDK 信息，但不得把必填公共维度只放在 batch 层而让事件失去自描述能力。

```json
{
  "event": "page_view | page_leave | performance | api | error | custom",
  "appId": "ops-admin",
  "env": "prod",
  "release": "1.4.2",
  "pageUrl": "https://example.internal/order/list",
  "pageRoute": "/order/list",
  "userId": "u_xxx",
  "deptId": "dept_xxx",
  "roleId": "role_xxx",
  "sessionId": "s_xxx",
  "deviceId": "d_xxx",
  "ua": "allowlisted-user-agent",
  "os": "macOS",
  "browser": "Chrome",
  "timestamp": 1787155200000,
  "payload": {}
}
```

事件映射规则：

| 当前事件 | v1.8 事件 |
| --- | --- |
| `page_view`、`page_leave` | 保持相同 `event` 值 |
| `web_vital` | `event=performance`，`payload.metric` 使用 `lcp`、`inp`、`cls`、`fcp`、`ttfb` |
| `error_js`、`error_resource` | `event=error`，`payload.errorType=js/resource` |
| `error_api` | `event=api`，通过 `payload.success=false` 和失败类型表达；正常请求也必须上报受控汇总以形成分母 |
| `feature_*`、long-view、workflow 事件 | `event=custom`，具体名称放入 `payload.name`；名称仍受 registry 和 schema 限制 |

R0 完成后只接受 contract v3，不接受 v1/v2 或上述旧字段别名。

| --- | --- | --- | --- |
| `dept_usage`、`role_usage` | 部门/角色活跃人数 / 编制人数及功能分布 | 未实现 | R4-C 由服务端目录聚合，必须返回目录版本与分母来源 |
| `role_feature_profile` | 角色 × 功能模块的 PV 与时长 Top N | 未实现 | R4-C 聚合；小群体保护和最小人数门槛 |
| `abnormal_access` | 非工作时间、高频、多设备或越权访问规则 | 未实现 | R7 只提供经管理层评审的固定规则和审计，不用于个人绩效 |

通用统计规则：

- 耗时类输出 P50/P75/P90/P99，页面默认 P90；具体指标明确指定 P75 时按该指标定义覆盖默认值；
- 比率必须同时返回 numerator、denominator、sample size、coverage、status 和 definition version；分母为 0 返回不可用，不返回 0%；
- 实时看板按 5 分钟粒度，自然日/周/月按项目时区；
- `main` 已实现但不在附件中的指标可以保留为版本化扩展指标，但不得占用或改义附件保留 key；
- 所有规范指标先在 R1-B 注册定义与实施状态，再由对应页面/模块里程碑补齐事实和查询；未实现时显示 `not_collected`，不得显示 0。

## 3. 产品定义

### 3.1 产品定位

Frontend Insight 是面向内部 Web 产品的前端监测平台。它通过用户行为、任务生命周期、浏览器错误和性能事实，为项目负责人、产品工程师和研发提供三类支撑：

1. **项目级判断**：项目在运行生命周期内的运营情况、前端质量和资产状态；
2. **业务级判断**：某个功能模块、功能或工作流是否被使用、是否完成、耗时是否合理；
3. **页面级判断**：某个页面的运营指标、错误、性能和复现上下文。

平台提供证据、偏离信号和调查优先级，不仅凭遥测自动宣布设计“好/坏”，也不用于人员绩效评价。

### 3.2 目标用户

| 角色 | 核心任务 | 权限 |
| --- | --- | --- |
| 项目负责人/Supervisor | 快速判断项目运营和质量状态，下钻低分原因 | viewer |
| 产品/运营 | 查看功能模块、页面、功能和工作流的使用与趋势 | viewer |
| 业务开发者 | 定位错误、性能问题和复现上下文，验证埋点 | viewer 或 admin |
| 项目管理员 | 管理项目、分析对象、指标、分数、探针和接口 | admin |
| 平台维护者 | 部署、链路健康、备份恢复和容量管理 | 运维权限 |

viewer 不能修改任何会影响指标、分数、采集或外部暴露范围的配置。所有 admin 修改必须写入审计日志。

### 3.3 设计原则

| 原则 | 要求 |
| --- | --- |
| 最多三层入口 | 全部项目 → 项目模块 → 详情抽屉/弹窗，不继续增加嵌套导航 |
| 项目先行 | 用户先选择项目，再进入项目分析；项目上下文始终可见 |
| 事实与判断分离 | 原始值、样本、数据状态、目标、公式和分数都可查看 |
| 运营与质量分离 | 两类指标、公式、版本和分数独立，页面可并列展示 |
| 单一语义来源 | 所有页面从同一指标定义/版本服务读取名称、公式、单位和状态 |
| 受控自定义 | 允许组合业务指标，不允许任意 SQL、任意代码或任意维度 |
| 版本不可变 | 激活版本不原地编辑，修改通过新草稿版本完成 |
| 数据状态优先 | 缺失、样本不足、延迟和 0 是不同状态 |
| 默认保护数据 | 不采集凭证、表单、DOM 文本、请求/响应正文和原始敏感标识 |
| 颜色有文字等价 | 绿色、黄色、红色符合常识，但颜色不能是唯一状态表达 |

## 5. 入口页：全部项目

### 5.1 目标

入口页展示已接入项目资产，使用户无需先选择下拉框即可回答：

- 当前有多少项目；
- 哪些项目运营或质量需要优先关注；
- 哪些项目链路不可达、数据过期或仍待配置；
- 最近一次数据更新时间是什么。

### 5.2 页面结构

页面为上中下三层：

1. 顶部：项目名称模糊搜索、新建项目；
2. 中部：项目卡片；
3. 底部：分页。

新建项目仅 admin 可见。弹窗至少配置项目名称、时区、允许 Origin、数据保留时间和初始指标模板；创建成功后刷新列表并定位新项目。

### 5.3 项目卡片

每张卡片显示：

- 项目名称；
- 运营分数；
- 质量分数；
- 项目状态；
- 链路状态；
- 最近数据更新时间；
- 缺少配置或样本时的原因；
- “进入项目”主操作。

分数不可用时显示“—”和原因，不能按 0 处理。

### 5.4 项目状态与颜色

附件正文的 80 分状态门槛和线框图的 85/60 颜色分段含义不同，v1.8 明确分开：

- **项目状态**：链路 healthy 且运营分数、质量分数均可用并高于 80 时为“正常”；链路 delayed/broken、任一分数不高于 80 时为“告警”；缺少配置或样本时为“待配置/数据不足”，不伪装成告警或正常。
- **分数颜色**：≥85 为绿色，60–<85 为黄色，<60 为红色，不可用为灰色。

颜色旁必须同时显示文字标签和触发原因。

### 5.5 列表行为

- 项目名模糊搜索，300 ms 防抖；
- 默认按“告警优先、最近更新倒序”；
- 支持 12/24/48 每页；
- viewer 只看到已授权项目；
- 无结果时保留搜索条件并提供清空入口；
- 卡片汇总接口不得为每张卡片产生独立 N+1 查询。

## 6. 项目概览

### 6.1 目标

用户进入项目后第一眼能够判断：

- 采集链路是否正常；
- 项目运营分数与质量分数；
- 哪个分数维度拖累总分；
- 主要运营指标当前值和变化趋势；
- 是否存在需要关注的固定告警。

### 6.2 页面组成

1. 链路状态、最近更新时间和“刷新数据”；
2. “项目运行情况”：运营雷达 + 运营分数、质量雷达 + 质量分数；
3. “运营指标”：当前激活版本中被标记为概览展示的指标卡；每张卡显示名称、值、单位、数据时间、业务描述和状态，超出一屏时使用可访问的美观滚动容器；
4. “指标变化趋势”：多选指标趋势；
5. “告警摘要”：P1，可配置展示；P0 复用现有固定告警。

### 6.3 运营分数

运营分数继承当前项目运营指数的解释性和门槛：

- 默认四维：使用覆盖 30%、持续使用与访问深度 25%、任务达成 30%、使用效率 15%；
- 可由分数管理创建新版本并调整维度、指标、目标和权重；
- 缺失值不按 0；
- 至少 3 个 eligible 维度且叶子权重覆盖达到配置门槛后才显示总分；
- 雷达图只展示 0–100 的维度分，不直接混入 PV、人数、毫秒等不同单位；
- 总分、维度、原始指标、目标、样本、版本和加权贡献可下钻。

v1.8 UI 使用“运营分数”，规范 key 为 `operational_score`；内部旧 `project_operational_index` 在对应模块重构时同步删除，不保留别名或面向用户的双术语。

### 6.4 质量分数

质量分数是独立业务指标，默认由以下维度组成：

| 维度 | 默认输入 | 方向 |
| --- | --- | --- |
| JS 稳定性 | `js_error_rate` | lower_better |
| 资源稳定性 | `resource_error_rate` | lower_better |
| API 稳定性 | `api_error_rate` | lower_better |
| 页面性能 | `lcp`、`inp`、`cls` 的规定分位数与目标符合度 | lower_better/target_range |

默认公式等价于“100 分基线减去错误和性能扣分”，但实际扣分阈值、上限和权重来自激活的质量分数版本，不硬编码在页面。

质量分数要求：

- 错误率分母和 Web Vitals minimum sample 明确；
- 链路 broken/delayed 时不生成可信分数；
- 没有足够 PV 或性能样本时返回 unavailable/insufficient；
- 不使用“没有采到错误”自动推断质量满分；
- 与运营分数使用不同 metric set/version；
- 默认不把数据链路健康本身当作质量加分，只把它作为可计算 gate。

### 6.5 雷达与趋势配置

- 每个分数可从已激活分数定义中选择 3–6 个维度用于雷达；
- 修改展示维度不修改分数公式；修改公式必须创建新版本；
- 趋势指标与“运营指标”同源；
- 原始不同单位指标不使用堆叠折线图；
- 同单位最多 4 条非堆叠折线；混合单位使用小多图或先选择单位组；
- 周/月粒度遵循公共时间规则，缺口不补 0。

## 7. 业务分析

### 7.1 功能模块

功能模块是用户定义的稳定业务分组，例如能源管理、设备管理、报警管理。现有 module 数据模型与附件 `module_penetration` 的语义一致，因此继续使用 module：

- 每个页面属于一个功能模块；
- 功能模块由 admin 显式配置，不从 URL 自动推断；
- 可设置顺序和状态；按 `R1A-D1-A` 删除模块级关键度，模块权重以后只能在有版本、公式和血缘的指标/分数定义中引入；
- 未归类页面继续显示基础数据，但不进入功能模块聚合和分数。

### 7.2 页面结构

1. 筛选层：功能模块单选、公共时间范围；
2. 业务运营指标：从当前运营指标版本选择的功能模块指标卡；
3. 指标变化趋势：与指标卡同源；
4. 工作流追踪：展示所选功能模块内关键工作流的开始、阶段达成、终态、耗时和异常。

默认指标使用字典规范 key，至少包括 `pv`、`uv`、`module_penetration`、`task_duration`、`operation_fail_rate` 和相关页面稳定性指标。只有单位、分母和聚合语义兼容的页面指标才能汇总为功能模块指标，不显示“产品稳定性”等没有固定公式的模糊指标名。

### 7.3 工作流定义

一个工作流由有序阶段组成：

| 字段 | 说明 |
| --- | --- |
| workflowKey/name | 稳定标识与业务名称 |
| moduleId | 所属功能模块 |
| startPolicy | 如何创建匿名 workflow instance |
| steps | 2–20 个有序步骤 |
| terminalPolicy | 成功、失败、取消、超时 |
| timeoutSeconds | 整体超时 |
| version/status | 草稿、激活、停用 |

步骤触发类型：

- 显式 SDK action；
- 稳定 `data-fi-action`/ID 选择器适配器；
- 受控网络请求完成；
- 页面生命周期，如加载完成或刷新；
- 与当前 workflow instance 显式关联的 operation 成功/失败/取消；独立 operation 不按 session 或时间邻近自动归入工作流。

普通 class 容易随样式变化，UI 可以录入但必须提示不稳定；推荐使用显式 SDK step key 或 `data-fi-action`。平台不默认扫描全部点击，不采集 DOM 文本。

工作流配置页必须说明“谁在什么条件下让步骤达成”，不能只展示 `SDK action`、`operation` 和“受控值”等内部术语。触发类型的用户术语、判定预览和长说明布局按 9.7.3–9.7.5 执行。

### 7.4 工作流事件流程

~~~mermaid
flowchart LR
    A["开始触发"] --> B["生成匿名 workflowInstanceId"]
    B --> C["步骤 1 达成"]
    C --> D["步骤 2…N 达成"]
    D --> E{"终态"}
    E -->|成功| F["completed"]
    E -->|失败| G["failed"]
    E -->|用户取消| H["canceled"]
    E -->|超时无终态| I["approximate_abandoned"]
~~~

每个事件携带 workflow instance、definition version 和 step key。同一工作流并发实例不能串联；业务 ID、设备 ID、报警 ID、人员 ID 不得作为 instance ID。

### 7.5 工作流指标

- started instances；
- 各阶段到达率和阶段流失；
- completed/failed/canceled/approximate abandoned；
- 总耗时 p50/p75；
- 相邻阶段耗时 p50/p75；
- 完成前页面数和功能模块跨度；
- 指标可用起始时间和定义版本。

点击按钮只表示步骤发生，不自动代表业务成功。网络请求成功也只有在工作流定义明确时才可作为终态。

## 8. 页面分析

页面是分析系统中的最小产品单元。页面分析包含“质量分析”和“运营分析”两个 TAB，默认质量分析。

### 8.1 公共筛选

- 路径：单选、支持模糊匹配，默认 ALL；
- 开始/结束时间：默认最近 7 天；
- 筛选写入 URL；
- 仅返回当前项目已授权数据；
- 路径使用规范 `pageRoute`，不暴露 query/hash。

### 8.2 质量分析

额外筛选“错误类别”：

- ALL；
- API/Ajax；
- resource；
- Vue；
- React；
- Promise；
- JS；
- other。

核心 SDK 保持框架无关。Vue/React 类别由可选适配器或显式安全字段产生，不能依靠上传源码或 DOM 猜测。

错误明细表至少包含：

| 列 | 要求 |
| --- | --- |
| 路径 | 归一化 `pageRoute` |
| 时间 | 项目时区，精确到秒 |
| 堆栈信息 | 脱敏且截断的首帧/有限帧 |
| 复现条件 | 结构化安全上下文，点击打开抽屉 |
| 类别 | 标准化错误类别 |

为控制高频错误量，列表支持 error group 折叠、游标分页和“只看最新一次/查看全部实例”。默认保留现有稳定 error group 能力。

“复现条件”只能包含：

- `pageRoute`、`release`、`env`；
- 浏览器/OS 家族和视口档位；
- navigation/lifecycle 类型；
- API 方法、脱敏路径和状态码；
- 已显式追踪的最近工作流 step key；
- SDK/schema 版本。

禁止包含 Authorization、cookie、header、query、请求/响应正文、表单、DOM 文本、账号原值、设备/报警/人员标识和录屏。

### 8.3 运营分析

1. 页面运营指标卡：从指标管理中选择的页面级运营指标；
2. 指标趋势：与卡片同源；
3. 页面模板、所属功能模块、核心状态和可用起始时间；
4. 页面内关键工作流/任务；
5. 未归类页面的 admin 配置入口。

默认保留 `pv`、`uv`、`vv`、`avg_usage_duration`、`hourly_distribution`、`bounce_rate` 以及按页面配置的工作流/任务指标。页面可见时长分位数、时长覆盖率和访问深度可作为扩展诊断指标保留，但不能替代字典指标；缺失 `page_leave` 不按 0 参与时长。

## 9. 指标管理

### 9.1 定位

指标管理是平台的配置与语义中心。入口页、项目概览、业务分析和页面分析不得维护各自独立的公式或指标名称。

页面包含：

1. 分析对象：功能模块、页面、工作流；
2. 运营指标；
3. 质量指标；
4. 分数管理；
5. 版本库。

### 9.2 用户术语与内部层级

| UI 术语 | 内部实现 | 示例 |
| --- | --- | --- |
| 原子指标 | fact/atomic 固定查询 | `pv`、`lcp`、错误次数 |
| 业务指标 | derived/composite DAG | `uv`、`module_penetration`、`js_error_rate` |
| 分数 | 0–100 composite | 运营分数、质量分数 |

系统默认原子指标由代码和固定查询提供。用户不能修改其底层 SQL，但可以在新版本中启用、停用、调整展示和引用。

### 9.3 受控业务指标公式

用户定义业务指标必须基于已注册指标，不直接基于任意列或原始事件。

允许的首版运算：

- `+`、`-`、`*`、`/`；
- `min`、`max`、`clamp`；
- `weighted_mean`；
- `normalize(higher_better/lower_better/target_range)`。

约束：

- 公式保存为经过校验的 AST，不保存可执行代码；
- 最多 20 个输入、8 层深度、100 个节点；
- 加减必须单位兼容；
- 乘除必须经过单位规则校验；
- 除数为 0 返回 metric_not_available，不隐式返回 0；
- 缺失值默认传播，不允许用 `coalesce(..., 0)` 掩盖数据缺口；
- 输入 entity scope 和时间粒度必须兼容；
- DAG 不能循环；
- 每个指标声明名称、业务问题、单位、分母、去重键、missing policy、minimum sample、owner 和版本；
- 服务端计算，前端不得独立实现另一套公式。

### 9.4 分数管理

分数是一类返回 0–100 的业务指标，包含：

- 分数 key、名称、类型（运营/质量）；
- 3–6 个维度；
- 每个维度的指标、目标、方向和权重；
- 总分展示 gate；
- 颜色分段；
- 雷达展示维度；
- 适用项目/功能模块；
- definition version 和 metric set version。

权重总和必须为 100%。未达到 minimum sample、缺少目标或数据延迟的分项不按 0；总分是否可显示由覆盖门槛决定。

分数内部统一保存 0–100 数值，展示单位可以选择“分”或“%”；切换展示单位不能改变公式、阈值或底层数值。

### 9.5 版本库

指标版本是完整快照，包含分析对象引用、指标定义、公式、启停、展示位置、分数定义和依赖版本。

~~~mermaid
stateDiagram-v2
    [*] --> Draft: 新建/复制版本
    Draft --> Validating: 保存并校验
    Validating --> Draft: 校验失败
    Validating --> Active: admin 激活
    Active --> Superseded: 激活后续版本
    Superseded --> Active: 重新激活旧快照
    Draft --> Abandoned: 放弃草稿
~~~

规则：

- 激活版本不可原地修改；
- 修改已激活指标时自动复制出新草稿；
- 激活前展示依赖、受影响页面、公式 diff 和测试结果；
- 同一项目、同一类型同一时刻只有一个 active version；
- 重新激活旧版本是选择旧快照，不是修改历史；
- 开发阶段可以清理测试数据，但版本不可变仍是产品能力，不能省略。

### 9.6 指标血缘

所有业务指标和分数必须能从结果沿 DAG 下钻到原子指标。血缘抽屉展示：

- 当前公式和版本；
- 直接上游与下游；
- 单位、样本和缺失规则；
- 被哪些页面、卡片、趋势和分数引用；
- 循环或失效依赖的校验结果。

### 9.7 R1-A 手工验收后的补充设计（已确认方案，文档评审已通过）

本节处理 R1-A 手工验收中暴露的分析对象生命周期、页面配置结构和工作流可理解性问题。2026-08-27 已确认并完成文档评审：`R1A-D1-A`、`R1A-D2-A`、调整后的 `R1A-D3-A`、`R1A-D4-A`、`R1A-D5-A` 和 `R1A-D6-A`。后续代码从已验收的 R1-A 代码基线创建独立实施分支，不在已合并的文档评审分支修改代码。

#### 9.7.1 已确认决策

##### R1A-D1：模块级关键度

**决策：D1-A，删除模块级关键度。** 当前 v1.8 分数公式只消费页面关键度；模块关键度没有公式、版本、血缘或明确消费者，继续保留会让管理员误以为它正在影响分数。因此从功能模块 UI、DTO、API、空库 schema、seed 和测试中删除该字段。保留页面关键度，因为它用于核心页面使用覆盖率和页面可见时长符合度。以后如需模块加权，只能在指标/分数版本中定义权重、公式、血缘和生效区间。

##### R1A-D2：删除、停用和归档

v1.8 的 R1-A 写了 CRUD，但当前删除接口实际等价于停用。三种动作必须分开：

- **停用**：暂时不用于新配置和计算，可以重新启用；对象及历史引用保留。
- **归档**：从默认列表和选择器隐藏，保留审计、历史归属和唯一 key；提供“显示已归档”和恢复入口。
- **物理删除**：数据库记录和引用不可恢复。

**决策：D2-A，只提供停用与归档，不提供产品内物理删除。** 归档前必须停用；功能模块仍有页面或工作流时禁止归档并列出依赖；页面和工作流归档后不进入普通列表、选择器或新配置，但历史分析仍能按原名称和版本解析。提供“显示已归档”和恢复入口，唯一 key 在归档后继续占用。开发/测试数据清理由 reset 完成，不能把停用按钮改名为删除。

##### R1A-D3：启用状态下允许修改哪些字段

**决策：调整后的 D3-A，启用状态允许修改，但按语义保留历史。**

- 永久标识 `moduleKey/pageRoute/workflowKey` 创建后始终不可修改；需要新标识时创建新对象并停用/归档旧对象。
- 名称、描述、展示顺序等展示字段可在启用状态直接修改并审计。
- 模块归属、页面模板、核心状态、页面关键度、预期频率等语义字段也允许在启用状态修改，不强制先停用。用户开始修改任一语义字段时，在字段旁常显提示：**“不建议频繁修改该字段”**；提示只说明历史口径和趋势可比性风险，不禁用控件、不阻止保存。
- 语义修改必须保存为新的配置 revision 和 `effectiveFrom`，并关闭上一 revision 的有效期；历史查询按事件时间关联当时生效的 revision，不能用当前值静默重写历史。
- 工作流已激活版本继续不可原地修改；点击编辑后创建或打开新草稿版本。用户可以在工作流仍启用时编辑草稿，不要求先停用当前激活版本，激活新版本时才关闭上一版本的有效期。

##### R1A-D4：页面定义采用模块优先结构

**决策：D4-A，采用模块主从视图。** 左上先选择功能模块，下面只显示该模块的页面；新增页面自动带入所选模块。列表列为页面名称、`pageRoute`、页面模板、核心状态、状态和操作；页面关键度与预期频率在编辑抽屉中展示。编辑时可以把页面移动到其他模块，并按 `R1A-D3` 创建新 revision、显示语义修改提示。该交互不改变“一页只属于一个功能模块”的数据模型。验收原型中的“所属模板”按页面模板处理，所属模块由顶部选择器表达。

##### R1A-D5：未归类 route 的位置

未归类 route 用于发现“已有访问事实、但尚未建立页面定义”的配置缺口。v1.8 的 7.1、8.3、15.4 和开发计划 R6 都要求它继续存在，因此不能在不修改产品口径的情况下直接删除。

**决策：D5-A，迁移未归类 route 入口。** R1-A 页面定义主视图不再长期展示大块未归类表格，只显示待处理数量和跳转；R6 在“页面分析 → 运营分析”按时间范围展示待归类 route，并允许 admin 预填创建页面定义。R6 上线前保留一个折叠的临时入口，迁移后删除临时入口。未归类页面继续显示基础数据，但不进入模块聚合和分数。

##### R1A-D6：选择器适配器的达成事件

**决策：D6-A，只支持用户激活事件。** 首版 selector adapter 只在匹配元素发生 `click` 或受控 `change` 时达成；不提供 `appeared`，不通过 MutationObserver 扫描元素出现。渲染完成、数据加载完成等结果必须使用显式 SDK 或受控生命周期/请求适配器。

解释图标不在所有工作流步骤中常驻。只有用户把“步骤达成条件”选为“元素交互”时，才在该选项/字段旁显示可键盘触发的说明图标，解释“首版只响应用户 click/change；元素出现不代表阶段达成”。同一要点同时进入右侧上下文说明区，完成配置所必需的信息不能只放在 tooltip 中。

#### 9.7.2 页面定义交互方案

按已确认的 `R1A-D4-A`，页面结构为：

1. 顶部模块选择器显示模块名称、状态和页面数量，默认恢复用户上次选择；停用/归档模块不进入普通新增选择器；
2. 页面列表显示当前模块下的页面，支持名称和 `pageRoute` 搜索；
3. “新增页面”固定在列表底部和区块右上角，打开抽屉后预填当前模块；
4. 页面编辑抽屉展示 route、名称、模板、核心状态、页面关键度、预期频率和状态；
5. `pageRoute` 创建后不可编辑；需要新 route 时创建新页面定义，并按生命周期规则停用/归档旧定义；
6. 保存、状态切换、归档和恢复都有明确结果反馈；失败时保留输入并把错误贴近相关字段。

#### 9.7.3 工作流配置的用户语义

“触发类型”在 UI 改称“步骤达成条件”。每种条件都必须表达主体、事件和匹配条件：

| 达成条件 | 主体 | 步骤何时达成 | UI 配置 | 不能推断 |
| --- | --- | --- | --- | --- |
| 显式 SDK 上报 | 业务开发者预先埋入宿主代码 | 业务逻辑确认阶段已经到达时，代码显式调用当前 workflow handle 的 `reachStep(stepKey)` | 生成包含 `workflowKey/stepKey` 的只读接入示例；不再填写重复的 `actionKey/受控值` | 配置本身不会自动产生事件；不能从任意点击或请求推断 |
| 元素交互 | 用户与已配置元素 | 匹配元素发生 `click` 或受控 `change` | 事件类型 + ID/`data-fi-action`/selector；仅在选中该条件时显示 D6 说明图标 | 元素出现或交互不等于业务成功；不采集 DOM 文本 |
| 请求完成 | 受控请求适配器 | 匹配方法和脱敏路径模式的请求完成并得到配置的传输结果 | HTTP 方法 + 路径模式 + 结果条件 | HTTP 2xx 不自动等于业务成功 |
| 页面生命周期 | 已配置页面 | 目标页面发生加载完成或刷新 | 页面定义 + 生命周期事件 | 页面加载不等于任务完成 |
| operation 终态 | 业务开发者预先埋入并与当前 workflow handle 关联的 operation | 指定 `operationKey` 的关联 handle 上报 `succeeded/failed/canceled` | 已登记 operation + 终态 + 只读接入示例；不能只有状态下拉框 | 独立 operation、HTTP 结果或同 session 的邻近事件都不能自动归到当前 workflow instance |

步骤达成条件和工作流终态策略是两个层次：前者回答“某一步何时到达”，后者回答“到达哪一步时整个工作流结束为成功、失败或取消”。超时继续固定为 `approximate_abandoned`，不得显示为业务失败。

每个步骤卡实时生成一条可读预览，例如：

- “当业务代码对当前工作流实例执行 `reachStep('property_rendered')` 时，本步骤达成。”
- “当用户点击 `[data-fi-action='download']` 时，本步骤达成；这不代表下载成功。”
- “当与当前工作流实例关联的 operation `model_download` 上报 `succeeded` 时，本步骤达成；工作流是否成功由下方终态策略决定。”

##### 显式 SDK 上报如何使用

显式 SDK 上报就是业务开发者在业务开发时预先埋入调用代码，明确告诉监测平台“这个 workflow instance 已到达这个阶段”。R4-B 的目标调用形态如下，最终签名随 SDK breaking Pre-1.0 ADR 一同冻结：

```ts
const workflow = tracker.startWorkflow("admin_model_download");

await renderModelProperties();
workflow.reachStep("property_rendered");
```

管理员负责在工作流定义中配置稳定的 `workflowKey/stepKey`；业务开发者从配置页复制接入示例，并只在真实业务阶段到达后调用。`workflowInstanceId` 由 SDK 生成，业务代码不能传入设备、订单、报警或人员 ID。

##### operation 终态如何使用

operation 表示一个有开始和唯一终态的可复用业务操作，例如“模型下载”“报表导出”或“告警确认”。当前 tracker 已提供 `tracker.startOperation(featureKey)` 以及 `succeed/fail/cancel` handle，并要求对应 feature 已登记且启用 operation lifecycle；它能正确配对一次独立操作，但当前事件只有随机 `operationInstanceId`，没有 `workflowInstanceId`，因此**当前独立 operation 不能直接驱动某个工作流步骤**。

R4-B 必须增加显式关联，目标调用形态为由当前 workflow handle 创建关联 operation：

```ts
const workflow = tracker.startWorkflow("admin_model_download");
const operation = workflow.startOperation("model_download", {}, "click");

try {
  await downloadModel();
  operation.succeed();
} catch {
  operation.fail("download_rejected");
}
```

SDK 在内部为 operation 与 workflow 生成随机实例关联；业务方仍不能传入 instance ID。禁止通过“同一 session 最近一个 operation”或事件时间邻近关系猜测关联，否则并发操作会串线。取消只能由明确的用户取消动作调用 `operation.cancel()`。

`operationKey` 的配置来源复用当前已登记且 `operationLifecycleEnabled=true` 的 feature 标识；UI 名称统一为“operation 标识”。实现时通过 ADR 收敛当前 `featureKey` 参数名和 v1.8 `operationKey` DTO，不提供两套可编辑标识。operation 的规范终态使用 `succeeded/failed/canceled`，与现有 SDK 状态一致；`completed` 只用于整个 workflow 成功终态。

两种方式的选择规则：

| 场景 | 使用显式 `reachStep` | 使用关联 operation 终态 |
| --- | --- | --- |
| 只需要明确告诉平台“某阶段已到达” | 是，接入最直接 | 否 |
| 业务动作本身有开始、成功、失败、取消和独立耗时 | 可用，但会重复写生命周期代码 | 是 |
| 同一业务动作会被多个工作流或独立操作分析复用 | 不推荐与某一 `stepKey` 强耦合 | 是 |
| 没有已登记 operation，或暂未升级到支持关联的 SDK | 是 | 不可用 |

R1-A 只保存和解释工作流定义，不要求产生工作流事实数据。选择 operation 终态时，配置页必须明确显示“需要已登记 operation 与 R4-B 关联 SDK”；在兼容 SDK/collector 上线前不得宣称该步骤已经可采集。

#### 9.7.4 说明内容与呈现方式

不能把所有说明都放进 tooltip。按信息长度和重要性选择载体：

| 内容 | 呈现方式 | 规则 |
| --- | --- | --- |
| 字段名称和主体 | 清晰可见的 label | 优先使用业务语言，例如“步骤达成条件”“匹配的 operation” |
| 填写必需的一句话 | 字段下方常显 helper text | 最多一句，说明格式、用途或最重要限制 |
| 非关键补充 | 问号图标 tooltip | 简短、可通过鼠标和键盘触发；不能承载完成任务必需的信息 |
| D6 元素交互范围 | 选中“元素交互”后出现的说明图标 + 上下文面板 | 未选中时不显示该图标；选中后说明只支持 `click/change`，不支持元素出现 |
| 较长的条件逻辑 | 桌面端右侧“配置说明”上下文面板 | 随当前选择的达成条件更新，包含适用场景、判定时机、示例和不能推断的内容 |
| 当前配置含义 | 步骤卡内自然语言判定预览 | 随输入实时更新，不要求用户自行组合内部字段含义 |
| 启用态语义修改 | 字段旁常显 inline warning | 用户开始修改时显示“**不建议频繁修改该字段**”；不禁用控件、不阻止保存，并说明保存后创建新 revision |
| 脆弱或有风险的配置 | 紧邻步骤的 inline warning | 不占用字段所在横向网格；说明风险和可执行替代方案 |
| 字段错误 | 字段下 inline error + 表单错误摘要 | 保留用户输入、移动焦点到首个错误，不只显示全局 toast |
| 创建/保存/启停结果 | 全局 toast/message | 成功简短确认；失败给出原因和下一步，重复 key 明确指出冲突字段 |
| 完整业务案例 | “查看示例”抽屉/链接 | 复用 18.4 的“大屏属性查看”和“后台模型下载”模板，不把长教程塞进表单 |

工作流编辑器桌面端采用“编辑区 + 右侧上下文说明区”；说明区使用页面现有空白，不挤压步骤字段。窄屏下说明区折叠到当前步骤下方。步骤字段、告警和删除操作分别占独立行，避免横向挤占。

#### 9.7.5 行业交互原则与可访问性

- Material Design 将 tooltip 定位为简短、具体的上下文支持，因此只用于非关键补充：<https://m3.material.io/components/tooltips/guidelines>；
- GOV.UK Design System 建议 hint text 保持短句，长逻辑不放在字段提示中：<https://design-system.service.gov.uk/components/text-input/>；
- Carbon Design System 建议 inline notification 靠近相关内容，字段错误同时使用字段级错误，并让消息给出下一步：<https://carbondesignsystem.com/components/notification/usage/>、<https://carbondesignsystem.com/patterns/forms-pattern/>。

tooltip、说明面板、判定预览和错误信息必须支持键盘，并通过 `aria-describedby` 与对应字段关联。颜色和图标不能成为唯一含义；切换步骤或提交失败后焦点位置必须可预测。

## 10. 设置

### 10.1 接入指南

- 展示 `appId`、接收 endpoint、允许 Origin 和 CSP；
- 按当前探针版本生成最小接入代码；
- 支持发送测试事件和查看链路状态；
- 明确 SDK 不读取 Authorization、Cookie、Local/Session Storage token、表单、DOM 文本和 URL query；
- 将项目基础配置、成员与 Origin 管理收拢到设置。

### 10.2 探针版本管理

页面显示：

- 当前推荐版本；
- 项目最近观测版本及占比；
- supported/deprecated/blocked 状态；

接口管理用于向 Prometheus 或获准的第三方系统暴露稳定读模型。

首版接口类型：

- 当前指标快照；
- 指标趋势；
- 错误组/质量摘要；
- Prometheus scrape。

表格列：

- 接口；
- 描述；
- 参数（悬浮 tooltip）；
- 状态；

### 18.2 指标单一来源的准确含义

指标按三层管理：

1. **原子指标**：每个原子指标只有一个受代码保护的事实查询或采集来源，用户不能复制、覆盖或改写其底层 SQL。例如 `pv` 只来自去重后的 `page_view` 事实。
2. **业务指标**：可以引用一个原子指标，也可以通过受控 DAG 引用多个原子指标或其他无环业务指标。例如 `uv` 是对用户标识去重后的单输入业务指标，`module_penetration` 同时需要目标功能模块用户数和项目用户数。
3. **分数**：引用已经归一化的业务评分项，不直接把 PV、人数、比例和毫秒相加。

“单一来源”要求指标管理中的当前版本是名称、公式、单位、分母、去重键、scope 和血缘的唯一发布源。入口页、项目概览、业务分析和页面分析只引用 `metricKey + versionId`，不得在页面组件、API controller 或导出逻辑中复制公式。同一业务指标有多个输入不违反单一来源；同一个 `metricKey` 在多个页面各自实现公式才违反。

### 18.3 默认运营分数公式与可用门槛

#### 18.3.1 两层加权模型

原始指标先按目标归一化为 0–100 的叶子得分。`clip` 表示把结果限制在 0–100：

- 越高越好：`S(x) = clip(100 × (x - floor) / (target - floor), 0, 100)`；
- 越低越好：`S(x) = clip(100 × (ceiling - x) / (ceiling - target), 0, 100)`；
- 目标区间：位于 `[targetMin, targetMax]` 时为 100；低于或高于目标区间时，分别线性下降，并在 `toleranceMin` 或 `toleranceMax` 处降为 0。

维度分数只对当前可计算的叶子项归一化加权：

`dimensionScore_j = Σ(score_i × leafWeight_i) / Σ(leafWeight_i)`

默认运营分数为：

`operational_score = 0.30 × 使用覆盖 + 0.25 × 持续使用与访问深度 + 0.30 × 任务达成 + 0.15 × 使用效率`

如果恰有一个维度不可计算但通过 18.3.3 的总分 gate，则只在可计算维度间重新归一化：

`operational_score = Σ(dimensionScore_j × dimensionWeight_j) / Σ(eligible dimensionWeight_j)`

缺失指标不按 0 处理；总分必须同时返回实际参与计算的维度、叶子项和重新归一化后的贡献，避免用户把不同覆盖情况下的分数误认为完全同口径。

#### 18.3.2 默认四维取数和参数

下表中的“叶子项”是分数直接使用的最低层业务评分项；它们仍可由一个或多个原子事实计算，并不等同于原始事件。

| 维度与总权重 | 默认叶子项 | 原始值公式或来源 | 维度内权重 | 默认归一化参数 |
| --- | --- | --- | ---: | --- |
| 使用覆盖 30% | 活跃用户目标达成 | `uv / 配置的目标活跃用户数`；未登录用户按 `deviceId` 兜底 | 40% | 越高越好，floor=0、target=1 |
| 使用覆盖 30% | 核心页面使用覆盖率 | `已访问核心页面的关键度权重之和 / 全部启用核心页面的关键度权重之和`；是否访问由 `pv > 0` 判断 | 35% | 越高越好，floor=0、target=1 |
| 使用覆盖 30% | 活跃日覆盖率 | `有有效活动的预期工作日数 / 查询范围内预期工作日数` | 25% | 越高越好，floor=0、target=1 |
| 持续使用与访问深度 25% | 跨日持续使用率 | `至少在两个项目本地日期活跃的用户数 / uv` | 40% | 越高越好，floor=0、target=0.5 |
| 持续使用与访问深度 25% | 单会话不同页面数 P50 | 按 `sessionId` 统计不同 `pageRoute` 数后取 P50 | 30% | 目标区间 1–4，容忍边界 0–8 |
| 持续使用与访问深度 25% | 单会话功能模块数 P50 | 按 `sessionId` 统计已归类 `moduleId` 数后取 P50；纯未归类会话排除，混合会话只统计已归类模块；披露有效/排除样本 | 30% | 目标区间 1–2，容忍边界 0–5 |
| 任务达成 30% | 关键任务加权成功率 | `Σ(成功实例 × 任务权重) / Σ(开始实例 × 任务权重)` | 70% | 越高越好，floor=0.5、target=0.9 |
| 任务达成 30% | 关键任务不利终态率 | `Σ((失败 + 取消 + 超时)实例 × 任务权重) / Σ(开始实例 × 任务权重)` | 30% | 越低越好，target=0.1、ceiling=0.5 |
| 使用效率 15% | 成功任务耗时 P50 | 成功工作流实例的 `完成时间 - 开始时间`；池化所有有效实例，每个实例赋任务类型权重，取累计权重首次达到50%的耗时；明细仍按字典 `task_duration` 输出 P50/P90 | 60% | 越低越好，target=60 秒、ceiling=300 秒 |
| 使用效率 15% | 核心页面可见时长符合度 | 每个核心页面先按其页面模板目标区间计算符合度，再按页面关键度加权平均；来源为有效 `page_view/page_leave` 可见时长 | 40% | 越高越好，floor=0、target=1 |

这些目标值是默认起步模板，不代表所有内部系统的通用业务标准。管理员首次启用运营分数时必须确认目标活跃用户数、预期工作日、核心页面、页面模板和关键工作流；未确认的项目显示“待配置”，不能直接使用默认值制造看似可信的分数。

#### 18.3.3 eligible 维度、叶子权重和配置体验

- **叶子项**：评分树最底层、直接产生 0–100 得分的业务评分项，例如“关键任务加权成功率”。
- **eligible 叶子项（可参与计算的叶子项）**：已启用、原始值存在、样本达到 minimum sample、归一化目标完整、版本与查询范围一致。任一条件不满足时保留原始状态和原因，但不按 0 参与。
- **eligible 维度（可参与计算的维度）**：该维度至少有一个 eligible 叶子项，因此可以得到维度分数。
- **叶子权重覆盖率**：`Σ eligible 叶子项的(维度权重 × 维度内权重) / Σ 全部已启用叶子项的(维度权重 × 维度内权重)`。

显示总分必须同时满足：

1. 采集链路状态为 healthy；
2. 至少 3 个维度 eligible；
3. 叶子权重覆盖率不低于默认门槛 70%；
4. 所有参与项使用同一指标/分数版本和同一 `env`，且查询范围没有跨版本混算。

示例：使用覆盖三个叶子均可用，贡献 30%；任务达成两个叶子均可用，贡献 30%；持续使用维度只有权重 40% 的“跨日持续使用率”可用，贡献 `25% × 40% = 10%`；使用效率不可用。此时有 3 个 eligible 维度，叶子权重覆盖率刚好为 `30% + 30% + 10% = 70%`，可以显示总分，但页面必须醒目标注“使用效率缺失、持续使用维度仅覆盖 40%”，并展示重新归一化后的贡献。

生产使用者不直接配置“eligible”状态：系统根据数据和样本自动判断。新建项目使用默认运营分数模板，配置向导只要求管理员填写可理解的业务信息；权重和 gate 放在“高级设置”。发布新版本前必须提供配置完整性校验、缺失项中文提示、预计可计算维度、叶子权重覆盖率和固定 fixture 预览。普通管理员可以使用默认模板完成配置，不需要理解内部术语；界面统一显示“可参与计算/不可参与计算”，`eligible` 只保留为 API 字段。

| 配置项 | 示例 |
| --- | --- |

### 18.5 Origin 是什么

Origin 是浏览器同源/CORS 语义中的“来源”，格式固定为 `协议 + 域名 + 端口`，例如 `https://factory.example.com` 或本地开发使用的 `http://localhost:5173`。它不包含路径、query 或 hash，也不是服务器 IP、页面路由或 HTTP Referer。

“允许 Origin”是项目的浏览器接入白名单：SDK 从未登记的 Origin 上报时，ingest 拒绝请求或不返回允许跨域的响应，从而降低他人盗用 `appId` 写入垃圾数据的风险。默认使用精确匹配，不允许 `*`；生产、预发和开发环境分别配置允许来源并保留审计记录。

### 18.6 指标版本切换、重算与页面显示

从 v1.0 激活到 v1.1 时，**原始事件和原子事实不重写**；受公式、目标、权重、分析对象或启停状态影响的业务指标和分数需要按 v1.1 重新计算。缓存和结果必须带 `metricVersionId + projectId + env + timeRange/granularity`，v1.1 的结果不会覆盖 v1.0。

切换流程：

1. 从 v1.0 复制草稿 v1.1，编辑后完成公式、单位、依赖、循环、样本和 fixture 校验；
2. 激活前执行影响预览，对管理员选择的历史时间范围试算 v1.1；预览不影响线上页面；
3. 激活时记录 `effectiveAt` 并原子切换 active version，同时失效受影响的业务指标/分数缓存；不清理原子事实和旧版本结果；
4. 当前页面只请求 v1.1；缓存未完成时显示“v1.1 计算中”和原子指标，不得把 v1.0 结果标成 v1.1，也不得短暂混合两个版本；
5. 重算完成后刷新受影响卡片、趋势和分数；响应与页面持续显示版本号、计算时间和数据可用起点；失败时保持 unavailable/recalculating 并允许重试；
6. v1.0 仍可通过版本库显式查看或重新激活。重新激活也是一次受审计的 active pointer 切换，不修改历史快照。

默认口径从 `effectiveAt` 向后生效，不静默改写更早历史。时间范围跨越版本边界时，趋势标出分界并分段显示，不跨版本连线，也不生成跨版本单一总分。若需要用 v1.1 回算更早区间，管理员必须显式发起“历史试算/回算”；结果仍按 v1.1 独立保存，完成前不影响当前激活页面。

### 18.7 同一项目的多环境接入与查看

同一个逻辑产品的 `prod/staging/dev` 默认接入为**一个项目、一个 `appId`**，每次上报通过规范字段 `env` 区分环境；不因为部署环境不同重复创建三个项目。

- 各环境使用各自的 SDK 配置值 `env` 和 Origin 白名单；如果接入可信后端工作流事件或导出接口，凭证也按环境隔离，便于单独撤销和限流。
- 功能模块、页面、工作流和指标定义默认由项目共享；事实数据、样本、缓存、指标结果和分数始终按 `env` 隔离计算，不允许把生产与测试数据聚合到一个值。
- 项目页公共筛选增加环境单选器并写入 URL，默认 `prod`。用户切换到 `staging` 或 `dev` 后，项目概览、业务分析、页面分析和工作流详情全部跟随同一环境；页面标题和导出文件必须显示当前环境。
- 跨环境比较只能作为明确选择的对比视图，不能进入默认总分、趋势或项目状态。

只有当两个环境实际上拥有不同的产品负责人、成员权限、数据保留策略或完全独立的业务配置时，才拆成不同项目；单纯为了区分生产、预发和开发环境不拆项目。

任一 Go 条件不满足时，不进入对应代码阶段；记录 owner、决策和复评条件。
