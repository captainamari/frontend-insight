# ADR-009：运营分析实体、页面模板与生效边界

- 状态：Accepted
- 日期：2026-07-29
- 对应基线：requirements-v1.6、mvp-plan-v1.3

## 背景

M0–M5 以项目、路由和功能为主要分析对象。M6 需要在不改写历史事实的前提下，表达智慧园区产品中的稳定业务模块、页面类型、关键任务、业务目标与日历。

## 决策

1. 分析层级固定为 `project → module → page → task/feature → operation instance`。
2. module 由管理员显式配置，以 `(project_id, module_key)` 唯一；不从 URL 自动推断。
3. page definition 以项目内归一化 route 唯一，绑定 module，并选择：
   - `monitoring_dashboard`
   - `analysis_view`
   - `task_operation`
4. 未注册 route 继续返回基础访问事实，但状态为 `unclassified`，不进入核心覆盖和项目运营指数。
5. 页面与任务关键度只来自显式配置，不以流量推断。
6. 默认从配置 `effective_from` 起参与评分；M6 不用当前配置静默重写更早历史。
7. 项目目标账号、预期活跃星期和 profile assignment 都保存版本或生效时间并写审计。
8. 任务实例 ID 由 SDK 随机生成；禁止业务 ID、设备 ID、报警 ID 或人员 ID。
9. 页面详情使用三类模板各自的目标/容忍区间。项目级“页面可见时长目标符合度”先逐页按模板归一化，再按页面关键度汇总；不先混合毫秒值，也不让三类页面共享同一方向。
10. 项目指数的求值起点取所选范围与当前 profile、运营设置、参与页面/功能配置生效时间中的最晚值；跨边界时返回实际 `evaluationRange` 和 `partial`，不把新配置套到更早事件。

## 后果

- 页面时长和深度可以按三类业务语义解释。
- route 变更需要管理员维护 page definition，避免静默归类漂移。
- M6 查询同时返回未归类活动和配置缺口。
- 如未来需要第四类模板，必须先证明现有三类无法表达并新增 ADR。

## 被否决方案

- 从 URL 第一段自动创建模块：动态路由和微前端会导致高基数与错误归属。
- 用流量自动判定核心页面：会把“入口问题”反向固化为低权重。
- 当前定义覆盖全部历史：会导致历史指数不可复核。
